## Day 1（2026-09-15）· 摸清战场，从 0 到跑通

### 1. 读要求

- **做了什么**：读 `CHALLENGE.md` 与 `rubric.json`，把「要交什么」和「怎么评分」抄成清单。
- **关键收获**：这个挑战考的不是"会翻译"，而是**信息获取与处理管线**。rubric 五个维度的权重是 contentAccuracy 25 / pipelineAutomation 20 / artifactCompleteness 15 / aiUsage 20 / reflectionQuality 20——**有 40 分（管线+AI 使用质量）跟"译得好不好"无关**。这决定了策略：先把管线搭对，再谈翻译。
- **踩坑**：一开始以为要"翻译 31 个页面"，把注意力全放在产量上。读完 rubric 才意识到 `pipelineAutomation` 要求「换一门课的资料，同样的流程能再次产出」——这意味着脚本必须参数化，不能一页页手写。

### 2. 盘点源材料

- **做了什么**：解开 `materials/CS146S_offline.zip`，清点资产。
- **发现**：31 个 HTML 页面 + 3 个 PDF + 离线站点镜像（`site/`、`assets/`、`slides_info/`）。
- **关键决策**：**以 HTML 为翻译输入，不以镜像里现成的 `.md` 为输入**。原因是镜像中部分页面的 Markdown 转换是失败的——正文在 HTML 里完整，`.md` 却只有 0～426 字节。
- **用到的 prompt 思路**：「先别翻，先告诉我这批材料里有哪些文件、各自多大、哪些明显是空的」——先做体检，后做手术。

### 3. 建术语表（94 条）

- **做了什么**：先扫一遍全部源文，抽出高频术语，建 `glossary/术语表.md`。
- **prompt 迭代过程**（重要）：
  - 第 1 版 prompt：「帮我列一份术语表」→ 产出泛泛，全是通用词，对翻译一致性没用。
  - 第 2 版 prompt：「只列这门课特有的、容易译歪的概念，并给出**每个词的统一译名**，注明哪些必须保留英文」→ 可用。
  - 第 3 版（最终）：「按类目分组（核心范式 / 安全 / 工程实践），每行给英文、标准译名、备注；产品名保留英文，缩写保留英文并在首次出现给中文全称」→ 得到 94 条可机器校验的锚点表。
- **踩坑**：最初想直接让 AI"边翻边保持术语一致"，结果长文一多就漂移。**术语表必须是独立产物，先冻结、再翻译**，这是本项目最重要的一条经验。

### 4. 搭流水线

- **做了什么**：写 `pipeline/extract.py`（HTML → 干净 Markdown，仅标准库）与 `pipeline/pipeline.py`（`extract` / `coverage` / `glossary` 三个子命令）。
- **技术要点**：抽取时剥离 `nav`/`header`/`footer`/`aside`/`form` 等每页重复的样板块——这些是导航和页脚，不是讲义内容。
- **踩坑**：第一次抽取把侧栏导航也抽进来了，导致译文里冒出"Getting started / Core concepts / Platforms and integrations"这类导航文字。**修法**：在抽取阶段就剥离，而不是在翻译后清理——在源头解决，比在下游补锅便宜。

## Day 2（2026-09-16 上）· 翻译主体，撞上上下文墙

### 5. 批量翻译

- **做了什么**：按页翻译，每页读英文 Markdown、套术语表、写中文到 `translated/<同名 stem>.md`。
- **进展**：顺利推进到 26/31 页。
- **踩坑（最大的一次）**：遇到**超长页**。`agentic-ai-threats.md` 源文约 5.3 万字节，一次性读进来会**上下文预算溢出**，读回来的内容中间有缺块。如果硬翻，必然漏译或编造。
- **错误应对（值得记录）**：第一反应是"分几轮读同一页、拼起来翻"。结果：轮次之间内容重叠、边界不清，反而更难保证完整性。

### 6. 改用「分片 + 合并」

- **改法**：
  1. 先把超长页按语义边界切成 `chunks/<stem>__p01..pN.md`（**分片是落盘的中间产物，可追溯**）；
  2. 逐片翻译，写到 `translated/_parts/<stem>__pN.md`；
  3. 最后按顺序合并为 `translated/<stem>.md`，并逐条核对锚点行（10 个攻击场景、每张表格的标题）是否都在。
- **结果**：合并后 37,723 字节 / 523 行，锚点行逐项对齐，覆盖度到 100%。
- **经验**：**长文翻译的正确单位不是"页"，是"语义分片"**；而且分片必须落盘，否则无法证明"没漏"。

### 7. 尝试外包给本地 Agent（失败）

- **做了什么**：想把这批重活交给本机 WorkBuddy 命令行 Agent。
- **结果**：连续报 `spawn workbuddy ENOENT`——本机没有这个可执行文件。重试一次仍然失败。
- **处置**：不再纠缠工具链，**改为自己按分片流程直接完成**。
- **经验**：工具不可用时，最快的路是换回已验证的手工流程，而不是调试工具。但要把失败原因记下来（见 AAR 卡点）。

## Day 3（2026-09-16 下）· 质量抽检，把"感觉还行"变成"有据可查"

### 8. 写质检脚本

- **做了什么**：写 `pipeline/qc.py`，做四类自动检查：
  - A 结构对等（源/译文的标题数、表格数、代码块数、链接数是否一致）
  - B 残留英文（译文正文里是否还有整句英文未译；排除代码块、行内代码、URL、表格载荷）
  - C 术语落地（术语表条目在译文中是否真的用了标准译名）
  - D 空壳页（源文件本身无正文的页面，译文是否有「无正文」说明）
- **为什么值得**：rubric 的 `aiUsage` 20 分要求「质量抽检有据」。**"我觉得翻得挺好"不是证据，脚本输出的报告才是。**

### 9. 处理误报（这步比写脚本更花时间）

- **问题**：第一版脚本报了 13 项结构差异 + 一批残留英文，看着像灾难。
- **逐条对账**（产出 `out/qc-struct-audit.md`，8242 字节）：结果发现差异分两类，**都不是漏译**：
  1. 源站抓取时混入的框架块（侧栏导航、页脚推广位、"about the author"），译文按资料包用途剔除；
  2. 源页用重复 H4 承载 10 个攻击场景（H4 33→23），译文改为场景级标题并**保留全部表格**。
- **代码块误报**：脚本把带缩进的代码围栏当成了普通正文，导致代码里的英文被报成"未译"。**修法**：在 B 类检查里先标记围栏行号并跳过。
- **逐字引用白名单**：`context-rot` 页里有 13 处英文，是**原文逐字引用的模型退化输出**（用来说明"上下文腐烂"现象）。这些是证据，翻掉就毁了。**修法**：加 `KEEP_EN_QUOTES` 白名单。
- **JS 载荷误报**：`mcp-introduction` 残留的 `prompt:` / `tools:` 是 JS 请求载荷，`Stytch vs. Auth0；...` 是产品名对比导航。**修法**：新增两条正则规则识别。

### 10. 硬伤修复（最后 7 项）

- **做了什么**：写扫描脚本全量查 32 个译文文件（185,301 字符），查出 7 项硬伤，逐条定性后**批量修复**：
  - **30 处被转义的 HTML 实体**（`&gt;` / `&lt;` / `&amp;`）：关键证据是**源侧同类实体计数为 0**——说明这些全是翻译过程中被"顺手转义"的伪影，可以安全还原。典型位置：`finding-vulnerabilities-claude-codex` 的能力矩阵表（`>25k`、`>5k` 等阈值）。
  - **2 处泄漏的内部标记**（`how-to-review-code-effectively`、`sast-vs-dast`）：AI 生成内容时把内部状态标记写进了正文，属真实错误，删除。
  - **1 处真错字**（"的的"）。
- **修复前后对比**：硬伤 7 项 → **0 项**；最终质检：结构 0 ｜ 残留英文 0 ｜ 术语 0 ｜ 缺译文 0。
- **一条重要教训（判据也会说谎）**：修复后的复检又报了 2 项——`devin-coding-agents-101` 的"叠字"和 `mcp-server-authentication` 的"码内中文"。逐条核对发现：前者是合法的语法重复（"现在在"），后者是代码里的中文注释（合法）。**问题在判据太粗，不在译文**。于是收紧检查规则（叠字只查真错字、`#` 行内注释不计数），复检归零。
- **经验**：**抽检脚本的误报和译文的错误一样要治理**。误报不处理，报告就没人信；而"改译文去迎合错误判据"是最坏的做法。

### 11. 发布攻坚：本机没有 git，怎么把 167 个文件送上去

- **卡点**：本机 `git` 依赖 Xcode 开发者工具、当前不可用；`gh` 不存在；没有 SSH key、没有钥匙串凭据。
- **错误应对（值得记录）**：第一反应是"让本地 Agent 代劳"，结果 `spawn workbuddy ENOENT`——连可执行文件都没有，白等一轮。**先确认工具在不在，再决定用不用它。**
- **正确解法**：绕开 git，直接用 GitHub 官方 REST API 把文件做成 blob → tree → commit → 更新分支。
  - **坎 1（权限语义）**：细粒度令牌能通过身份校验，但 `POST /user/repos` 返回 **403 Resource not accessible**——它没有建仓权限。教训：令牌"能登录"和"能建仓"是两件事，报错要读到具体端点。
  - **坎 2（空仓库首提交）**：换经典令牌（`repo` 权限）后建仓成功，但空仓库的首次 Git Data API 写入被拒（409）。解法：先用 Contents API 落一个初始化提交，再推正式内容。
  - **坎 3（限速）**：加节流（约 75 次/分钟）+ 403/429/5xx 自动重试，167 个文件 / 22.3 MB 一次推完。
- **验收方式（关键）**：不信"脚本打印了成功"，而是用**公开只读接口回查**——`/repos/.../git/trees/<sha>?recursive=1` 返回 **167 个 blob、23,415,418 字节、`truncated=false`**，与本地待推清单逐项对齐。
- **经验**：涉及"发布/外部账号"的交付物，**第一天就确认环境依赖**；确认不了时，先找"不依赖它的等价通道"（这里是 API 直推），而不是硬修环境。

## 全天用到的 AI 能力清单

| 环节 | AI 用在哪 | 人（我）把关在哪 |
|---|---|---|
| 读要求 | 提取 rubric 五维度与红线 | 判断"管线分比翻译分重要"这个策略含义 |
| 抽术语 | 扫全文抽高频概念 + 生成译名表 | 判定哪些必须保留英文、哪些译名更自洽 |
| 抽取正文 | 生成 HTML→MD 解析脚本 | 决定剥离哪些样板块、验收抽取结果 |
| 翻译 | 逐页/逐片生成中文 | 术语一致性校验、锚点行核对、超长页分片决策 |
| 质检 | 生成四类检查脚本 + 结构差异对账 | 逐条判定"是漏译还是框架块"、拿主意修哪边 |
| 修复 | 生成实体还原/标记删除脚本 | 用"源侧计数为 0"证明可安全还原 |
| 发布 | 用 GitHub 官方 REST API 直推（blob → tree → commit → 更新分支） | 判定令牌是否真有建仓权限、用公开接口回查真实文件数验收 |

**一句话总结**：AI 负责"做"，我负责"定标准、判真假、拿主意"。整条链上最容易出错的地方不是翻译质量，而是**没人判断"这个告警到底算不算问题"**。
