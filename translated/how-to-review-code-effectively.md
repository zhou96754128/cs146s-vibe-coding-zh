作为 GitHub 的一名 Staff 工程师，代码评审是我日常工作中的主要关注领域之一。在过去的八年里，我评审了超过 7,000 个拉取请求（pull request，PR）。为什么这么多？因为代码评审对于构建优秀的软件至关重要，而另一双眼睛往往能发现你本来会遗漏的问题。

我把代码评审视为自己工作中最重要的环节之一。事实上，每当看到队友有一个准备好接受代码评审的拉取请求，我更愿意放下手头正在处理的分支，先去评审他们提出的改动。毕竟，他们的拉取请求已经通过了持续集成（continuous integration，CI）的层层考验，也达到了他们自己判断"完成"的标准，所以它很可能比我手头尚未完成的工作更接近可发布状态。我更愿意把他们的代码送过终点线，而不是再耗费无法预估的时间去完成我自己的代码。

我越早给出反馈——"这里可能为 nil 并导致错误""这看起来像是一个 n+1 查询""这里最好有个方法签名"——这些反馈就能越快得到处理，缺陷越快被消除，功能越快被交付。

我想分享一下我进行代码评审的方式，希望我们都能交付更好的代码。

## 什么是代码评审？

严格来说，代码评审——在 GitHub 上通过拉取请求评审来进行——让协作者可以就拉取请求中提出的改动发表评论、表示对改动的批准，或在拉取请求被合并前请求进一步修改。

我把拉取请求看作一段对话的开端。我把它读作作者在说："我认为这改善了我们今天已有的东西。"代码评审是塑造产品实现方式的大好机会。作为代码评审者，我的职责是与作者来回讨论，通过提问、质疑假设，以及整体上充当另一双眼睛，来改进他们的代码。

## 优化你的代码评审流程

### 如何找到待评审的拉取请求

我常驻在我的 GitHub 通知收件箱里。它是我在浏览器里固定标签页的少数几个之一，所以它总是触手可及。每当我等待 CI、处于任务间隙、开始一天工作，或只是有空闲时间时，我都喜欢查看收件箱。我评审的绝大多数拉取请求都是在那里找到的。GitHub 的各团队往往有一个特定的 Slack 频道作为大本营，那是分享"待评审"拉取请求的好地方——这也是我发现拉取请求的主要方式之一。

我还发现用 GitHub Slack 集成把某个 Slack 频道订阅到我团队相关的新拉取请求上很有用。为了筛选出现在 Slack 中的拉取请求，我会使用某个团队专属的标签，然后在 Slack 里用一条 'subscribe' 命令，例如 /github subscribe your/repo pulls +label:"your-team-label"。

我喜欢用诸如 is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team 这样的查询来搜索可能需要评审的未处理拉取请求。用这个查询，我可以找到 GitHub 组织内、未归档、非草稿，且将相关 codeowner 团队列为请求评审者的开放拉取请求。我通常会省略 review:required 这个搜索限定符，因为即使某位队友已经评审过，我仍有兴趣评审该拉取请求。毕竟，评审代码不仅帮助作者，也帮助我跟上影响我所负责代码的变动。

### 用评审者团队管理通知

你不希望代码变动去打扰一个庞大到团队里每个人都觉得评审这个改动不是自己责任的团队。这可能导致拉取请求要么无人评审而搁置，要么在还不该合并时就被合并，因为关键评审者在海量通知中漏掉了它们。这两种情况都会影响产品质量。

如果可行，我建议精简你所加入的 code owner 团队数量，让通知保持在可管理的范围内。如此一来，落到你收件箱里的拉取请求就不只是噪音，而确实是你觉得自己应该评审的东西。虽然庞大、什么都管的 code owner 团队作为兜底选项还可以，但作为自动评审请求的第一线默认设置并不理想。把仓库的 CODEOWNERS 文件整理好，并配合定义清晰的代码边界，以限制通知量，帮助评审者避免通知疲劳。

限制基于团队的通知的另一种方式是创建一个 first responders 团队，然后用自动化按排班来添加和移除团队成员。这样可以让团队专注于他们日常的代码库，而排班中的 first responders 会收到你团队服务区域内拉取请求的通知。例如，使用 PagerDuty API，你可以确定某天谁是 first responder。然后你可以用 Octokit 库来添加和移除团队成员。

### 用自动化在各团队间统一代码评审规范

仓库层面的配置和自动化，例如使用 CODEOWNERS 文件和分支保护规则，有助于在各团队间强制执行评审流程标准。其他标准，例如拉取请求里什么值得评论，则必须由我们人类来维护。把你们团队的代码评审方式记录下来，确保任何提供代码评审或提交拉取请求的人都知道如何让自己的拉取请求得到评审、评审的预期周转时间，以及正在使用哪些自动化来促进评审。

有些团队用项目看板来跟踪哪些拉取请求进来等待评审；我见过这对一个管理共享 API 的团队效果很好，这个领域经常被团队外的人修改。其他团队只依赖 GitHub 通知，我见过这在代码所有权范围界定得很紧、且团队对进来的拉取请求严格按时评审时效果很好。

如果你遵循的是你团队特有的流程，自动化可以帮助你与团队外的人沟通期望。例如，如果许多其他团队依赖你们团队的评审，你可以用一个机器人自动在任何请求你们团队评审的拉取请求上留下评论，告诉作者什么时候能等到你们的回复。

## 什么样的代码评审是好是坏？

好的代码评审能增加清晰度，并推动代码朝着比起点更好的状态前进。

作为评审者，沟通清晰是关键。你要弄清楚自己的哪些评论是个人偏好，哪些是批准与否的阻塞项。为你建议的做法提供一个例子，可以提升你的代码评审，让你的意思更清楚。如果你能提供来自与拉取请求同一仓库的例子，那就更好了——通过鼓励一致的实现方式，这进一步支持了你的建议。

相比之下，糟糕的代码评审缺乏清晰度。例如，一句不加任何评论的一概批准或一概拒绝，会让拉取请求作者怀疑这次评审是否彻底。哪怕只是重申你对拉取请求作者意图的理解并给出批准，也能揭示你和作者是否理解一致。

一次不明确说明其建议何时应该落实的代码评审，对作者来说也可能是糟糕的体验。指出已有的、未改动的代码应该被重构，或应该处理一个额外的情况，这没问题，但重要的是要说明这些是否是批准的前提条件。如果拉取请求在你的建议未被采纳的情况下也可以合并，一定要说出来。保持较小的 diff 并把那些改动作为单独的拉取请求分别交付，可能更安全。

这里有一条代码评审评论，它体现了具体性，并清楚地传达了建议的实现方式：

"我看到你的新方法与这个文件里现有的风格一致，接收了 [X] 个参数。拥有这么多参数会损害可读性，也意味着这个函数做得太多了。你觉得在后续的拉取请求里重构这个方法以及现有的那些方法，以减少它们接收的参数数量怎么样？"

这条评论做得好的地方：

- 提供了具体的细节。
- 引用了具体的代码或问题。
- 为问题建议了一个解决方案。
- 引用了证据或给出了解释。

在另一个极端，这里有一些可以写得更好的评审评论示例：

"我不喜欢这个。"——评审者不喜欢什么？他们心里有可以明确说出来的替代方案吗？

可以改进的地方：

- "这一行做的事太多，我们能简化它来提高可读性吗？"
- "我认为这会有性能问题，因为存在一个 n+1 查询。"
- "我们能改用 [首选框架] 的解决方案，而不是自己写一个自定义实现吗？"

"这行不通。"——为什么这些改动行不通？

可以改进的地方：

- "这行不通，因为 [X]，参见这个相关问题：[issue link]。"
- "这个以前在 [pull request link] 里试过，因为 [X] 行不通。"
- "如果你在 [X] 上遇到问题，可以试试 [alternative approach]。"

"我认为这修复了一个 bug。"——我很喜欢这个提醒，但有没有额外的上下文，比如一个 issue 链接，能让它更清楚？

可以改进的地方：

- "我认为这修复了 [issue link]。"
- "这是在修复来自 [issue link] 的 bug 吗？"
- "这看起来像是我们在 [link to failing build] 里遇到的那个 bug。谢谢修复！"

## 如何给出好的代码评审

### 提问

我把拉取请求作者视为对这次拉取请求所做改动拥有最多上下文的人。我可以基于我的经历——我在 Ruby on Rails 单体应用、TypeScript 中工作的经历，或与一个流量很大的数据库打交道的经历——指出我看到的问题，但我信任作者对我问题的回答。我视他们对具体细节的理解为比我的更好。

我也很喜欢提涉及代码中所做假设的问题。他们处理的数据是什么形状的？是否存在与该形状不符的数据？代码能很好地应对吗？代码是否资源密集？它的性能会好吗？作为评审者，我最喜欢的回应是作者提供一个自动化测试来验证这些场景下的行为。我第二喜欢的回应是经验数据，比如来自我们数据仓库的一个查询，或一张说明为什么那些场景不成问题的 Datadog 图表。

作为拉取请求作者，我很感激收到问题。当有人提问时，我就有了空间来解释为什么我对自己的改动有信心，必要时引用 issue、查询或图表。这也让我能把自己的知识和经验分享给他人。作者不仅能看到我的回应，其他评审者以及日后可能追溯某个过去决定上下文的读者也能看到。

### 给予肯定

除了提问，对拉取请求中你认同的部分发表评论也是一种好做法。这些评论可以表明你阅读并理解了正在被改动的内容，或者你验证了代码中的某个假设。这里有几个例子：

- "看起来这与该模块中其他类所用的模式一致。"
- "感谢为这个添加了测试！"
- "这比之前可读多了。"

根据我的经验，身处接收这类评论的一方也很舒服。收到代码评审有时会让人感到消耗。当我要应对来自好几方的提问和建议时，收到几条不向我索取任何东西、反而支持和认可我已投入的工作的评论，会是一种很好的鼓励。

### 留意偏见与假设

你很容易让对评审者、或对他们所改动代码领域的偏见影响你的评审。你习惯了某人在某个领域工作或拥有某种资历，就假定他们知道自己在做什么——但每个人都会犯错。你用眼睛盯着他们的改动，用提问去检验他们的假设或验证你自己的假设，就能在部署之前抓住问题。

我很推崇写测试，因为测试能消除一部分偏见。当你写一个测试来检查代码是否正常工作，你就不必只凭作者的一面之词，你只需看测试是否通过——当然，前提是你的测试写对了。😅

我也很推崇初级开发者在代码评审中向资深开发者提问，即使他们觉得自己的问题很傻或有显而易见的答案。如果它对你来说不明显，那就是合理的。对别人来说也不会明显！提出问题，给作者留出把答案写下来的空间，并为后来者保存这一点点教育。

### 批准还是不批准

我把自己的评审看作一道可能阻止别人改进我们产品的阻塞关卡，所以我会尽责地暂缓批准。我常常会持有个人偏好，并提出我希望作者做出的可选改动，但我不会仅凭这些就暂缓批准。如果我对某人的拉取请求有建议，但他们的拉取请求照原样并不会破坏生产、不会对用户产生负面影响，也不会以其他方式造成问题，我就会带着这些评论批准它。作者可以选择在合并拉取请求前处理我的反馈，也可以在另一个分支里跟进。

评审代码时，要牢记你的建议有多重要。它是否值得为了让它得到处理而推迟发布？是否值得走完整个循环：作者看到你的反馈、做出建议的改动、等待 CI、重新评审、部署，最后合并？如果某个建议没有被采纳也不会让谁的日子更难过，那就让作者决定是否以及何时做出这个建议的改动。

'Request changes'（请求修改）选项会阻止拉取请求被合并，直到评审者回来批准它。我极少使用它，因为它通常感觉太强硬了。我信任我的团队知道何时该批准一个拉取请求，所以队友的批准可以代替我的批准。同样，我信任拉取请求作者会尊重并考虑我的反馈，而不是因为别人批准了、而我没有，就盲目合并。我大概唯一会选 'Request changes' 的场合，是我认为存在一个紧迫的安全问题、并且担心他们在合并前不会看到我的顾虑。

## 如何从代码评审中获得最大价值

### 评审你自己的代码

GitHub 资深软件工程师 Paul Smith 教会我在请别人评审之前先评审自己的拉取请求，我也建议你这样做。先做一遍通读，对那些不明显的变化、或者如果出现在别人的拉取请求里你会追问的变化，留下行内评论。自我评审也能帮助判断一个拉取请求是否太大、是否适合拆分。

特别推荐：如果你在意让自己的拉取请求保持小巧，可以利用 lerebear/sizeup-action 自动给拉取请求打上标签，标明它们的复杂度和大小。

### 欢迎合并后的评审

如果我碰巧在有人有机会评审之前就合并了一个拉取请求，我仍然欢迎他们的评审。如果我的拉取请求破坏了什么或有非预期的后果，在拉取请求上把这一点评论出来，就留下了那条面包屑线索，帮助后来的读者弄清发生了什么！

如果我收到对一个已合并拉取请求的评审，我会像在拉取请求合并之前那样处理这些反馈。也许那是一条解释我观点的评论，也许是额外的拉取请求来迭代我最初交付的代码。也许是开新的 issue 来记录还需要完成的工作。

### 使用草稿拉取请求

当你创建一个新的拉取请求时，你可以选择把它设为草稿。我大量依赖草稿阶段来表明我是否想要评审。例如，如果一个必需的 CI 构建正失败，或者我只是还没完成，我就会把它保持为草稿。我也倾向于这样看待别人的拉取请求：如果它是草稿，我就假定作者还没准备好接受评审。如果它被标记为准备好评审，我就假定它只差获得足够多的批准就可以部署了。

草稿状态意味着一个拉取请求尚未完成，所以在解决合并冲突或处理评审者反馈时，我会把拉取请求移回草稿。如果我必须修改代码，我会先把拉取请求标记为草稿，以免让已经评审过的人不堪重负。当我把它移回 'ready'（就绪）时，它会向那些评审者发送一条 GitHub 通知，让他们可以再看一遍。

### 保持友善

"用蜂蜜比用醋能捉到更多苍蝇"这句话浮现在我脑海中。我希望自己的拉取请求得到评审，所以我喜欢回复拉取请求上的评论——尤其是我不同意评审者的时候。即使我不写回复，我也常常用一个 👍 来表示我同意，或用一个 ❤ 来说谢谢。

我希望评审者相信他们的建议不会被遗忘，所以我通过评论让他们持续了解进展。如果我同意他们的建议——比如进一步重构现有代码——我可能会这么说，同时也对在当前拉取请求里做这个改动提出异议。当我在后续拉取请求里处理他们的反馈时，我会回来提供一个链接，让评审者知道他们的反馈没有被忽视。

我也会在后续实现建议改动的拉取请求里 @ 他们，并附上一句说明："这处理了 @某某 在 中提出的反馈。"这既为其他读者提供了上下文，也相当于对原评审者的一次公开致谢，把功劳归于提出这个想法的人。

当你兑现"在后续分支里处理反馈"的承诺时，这有助于与评审者建立信任，从而让他们更放心地批准你未来的拉取请求，因为他们知道你不会留下未完成的东西。

## 结语

代码评审对产品质量的重要性怎么强调都不为过，尤其是在 AI 代码生成的时代。在我的职业生涯中，有很多次仅仅因为多了那一双眼睛，就抓到了一个 bug 或避免了一次事故。代码评审非常值得投入时间，无论是花在日常评审、打磨流程，还是构建支持它的自动化上。对开发者来说，现在彻底评审拉取请求，比日后处理一个已经交付到生产环境的问题要更快、更少痛苦。

感谢你对代码质量如此在意，愿意读我关于代码评审的理念。你最近检查过自己的评审队列吗？也许现在正是把这些想法付诸行动的好时机。

如果你想进一步了解如何在 GitHub 上使用拉取请求评审，可以看看 GitHub Community 上由 Staff DevOps Architect Mickey Gousset 和 Staff DevOps Architect Joshua Johanning 撰写的文章，讨论《评审拉取请求的 5 个技巧》（5 Tips for Reviewing a Pull Request）。
