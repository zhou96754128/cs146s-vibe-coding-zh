# 规格说明已死，规格说明万岁！（The spec is dead, long live the spec!）

### 原型是新的规格说明，规格说明是新的……源代码？

> 作者：Ravi Mehta（客座作者：Danny Martinez）
> 原文日期：2025 年 7 月 31 日

回顾我的职业生涯，规格说明（spec）变得越来越短。我刚进微软时，一名产品经理（PM）的分量，是用其规格说明的重量来衡量的。多年后在 Tripadvisor，我们把那位带着一张写在餐巾纸上的规格说明来参加产品评审的 PM 奉为传奇。

产品团队往往把规格说明当成文书工作——一种在“真正的工作”即交付之前不得不做的例行苦差。工程师因优雅的代码而受表彰，设计师因精美的用户体验而受表彰，PM 因交付了影响而受赞许。但规格说明呢？它们通常被草草写就、随手一扔、然后遗忘。

这从来都是个错误。在我的《产品能力工具箱》（Product Competency Toolkit）中，「特性规格说明」（Feature Specification）高居榜首——在十二项能力中位列第一——这不是没有原因的。它与「产品交付」和「产品质量」一起，共同支撑着「产品执行」。

**无懈可击的执行是优秀产品管理的基石，而一份出色的规格说明，正是这条赛道的起点。**

如今，我们构建产品的方式正在改变。工程师变得更快——快得多。AI 能在几分钟内把粗糙的想法变成能运行的代码。瓶颈不再是「构建」，而是「知道要构建什么」，以及让团队围绕这些需求对齐。

突然之间，这份卑微的规格说明不再是转瞬即逝的文书。它是产品管理的根基——它正在成为源代码本身。

## 为什么 PM 突然成了瓶颈

在最近一场题为《用 AI 更快地构建》的演讲中，吴恩达（Andrew Ng）指出了一个前所未有的趋势：

> “这是我这辈子第一次看到，有人向我提出‘PM 数量是工程师两倍’的团队方案。我还不知道这个方案是不是好主意，但我认为这是世界走向的一个信号。”——吴恩达

这印证了我们在上一篇文章中的预测：当工程师借助 AI 把交付速度提升数倍，公司需要的是**更多**的 PM 来支撑这些高产工程师，而不是更少。

随着产品交付的加速，产品管理的其他所有方面都承受着巨大压力——理解客户需求、打磨正确的功能、验证影响。

而所有这些压力，最终都聚焦到一件东西上——**规格说明**。

## 规格说明——新的源代码

在传统软件开发中，程序员编写人类可读的“源代码”，它被编译成高度优化、机器可读的“目标代码”。“目标代码”（也叫二进制）是一种副产品，可以用源代码重新生成。源代码，字面意义上，就是真相之源（source of truth）。

来自 OpenAI 的 Sean Grove 提出了一个颇具挑衅意味的论点。在他最近的演讲《新代码》（The New Code）中，他主张：**一份写得好的提示词（也就是规格说明）就是新的源代码**。

从这个角度看，我们做 AI 开发的方式完全是本末倒置的。我们精心打磨提示词，向模型传达我们的意图。AI 生成代码。然后我们**保留代码、丢掉提示词**。

> “这感觉就像是，你把源代码撕碎了，然后非常仔细地对二进制做版本控制。”——Grove 观察道。

想想看。在传统编程里，源代码是神圣的。源代码里包含着注释、结构和文档——理解并修改系统所需的一切。二进制只是一个下游产物。

但有了 AI，我们颠倒了这层关系。我们把生成的代码当作值得保留的产物，而把规格说明——提示词——当作用完即弃的东西。

Grove 认为这恰恰搞反了。代码，即便是优雅的代码，也只是他所说的规格说明的“有损投影”（lossy projection）。就像反编译一个二进制无法还原出原始的注释和变量名一样，读代码也无法告诉你它背后的完整意图。

而规格说明，则包含了一切。一份足够健壮的规格说明，能够生成“优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客”。

> “一份足够健壮的规格说明，能生成优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。”——Sean Grove，OpenAI

更重要的是，规格说明做到了代码做不到的事：**它让人类和机器在共同目标上对齐**。Grove 说得很直白：“一份书面的规格说明能有效地把人类对齐起来，它是你用来沟通、讨论、辩论、引用和同步的那件产物。”

他预测道：“在不远的将来，沟通最有效的人，就是最有价值的程序员。而且从字面意义上讲，如果你能有效地沟通，你就能编程。”

**新的稀缺技能不再是编码，而是撰写能完整捕捉意图与价值观的规格说明。**

对产品经理来说，这应该很耳熟。这正是我们一直在做的事——只不过现在，机器也在倾听了。

## 等等，原型不是干掉了规格说明吗？

直到最近，产品生命周期还不得不从规格说明（或 PRD、概念文档、餐巾纸）开始，由它来启动最初的线框图、设计、原型和 MVP 开发。

传统方式总让人觉得是种必要的恶。工程师做出基础 MVP，只为把点东西——任何东西——送到客户手里。“如果你不对产品的第一版感到难为情，那你就发布得太晚了”成了一句金科玉律。

而我们构建产品的整套方法，最近经历了一次重大转变。在这个新世界里，规格说明往往成了**输出**，而不是输入。

今天，你一行代码都不用交付，就能把原型送到客户手中。像 **v0**、**Lovable** 和 **Replit** 这样的工具，让你在几小时而不是几周内就能构建出可运行的原型。完全不需要工程。

这不只是更快——它是根本性的不同。手握一个“vibe 编码”出来的原型，你可以在写下特性规格说明的任何一行之前，就收集到真实的客户反馈。你可以检验假设、迭代流程、打磨交互。

- 旧工作流长这样：模糊想法 → 线框图 → 设计 → 工程师搭建的 MVP → 客户反馈 → 痛苦的规格修订 → 线框图 → 设计 → 重建 → 祈祷。
- 新工作流：模糊想法 → 快速原型 → 客户反馈 → 无比清晰的规格说明 → AI 辅助实现。

**原型并没有杀死规格说明。它们让规格说明变得更好。**

## 实践中的规格驱动开发

我们来看一个实操案例，看看这一切是如何展开的。Danny Martinez 是 **decimals** 的创始人，这是一个（尚处隐名阶段的）平台，帮助创作者经济中的专家，把自己人脉网络里的人才推荐到岗位上。

Danny 将带我们走一遍他们的规格驱动开发流程——这个流程带来了两方面的成效：

- 对于较大的功能，极大地改善了与工程的沟通；
- 让 Danny 这个没有任何编程经验的人，能一路从详细规格说明走到上线功能（针对那些较小的需求）。

下面交给 Danny……

> 这是我最近做的一个例子。先交代背景：我们正在做一款产品，让专业的影响者（influencer）能把自己人脉网络里的候选人推荐到岗位上。上线了一个新的落地页（landing page）之后，我们需要给这些专家一个快速访问自己页面链接的方式。
>
> “我们需要在页头放一个按钮，指向公司申请页。我眼下正忙着邮件的事。如果你能接，这个活儿是 vibe 编码能搞定的。”
>
> 这是我联合创始人发来的，说的是一个需要上线的简单按钮。够简单，而且正是那种非技术人员现在能自己交付的东西。

下面是让这个按钮在几分钟内上线的配置与步骤：

- 项目管理工具：**Linear**
- IDE：**VS Code**
- 扩展：**GitHub Copilot Pro**
- 模型：**Claude Sonnet 4**
- MCP 服务器：**Linear MCP 服务器**，让 Copilot 能访问 Linear 工单

来看看流程中的步骤（可对照上面的 Loom 视频）：

- 从联合创始人的 Slack 消息里生成一条 Linear 工单（00:14）
- 在上面的工单里明确我想要的新文案（00:25）
- 打开 Copilot，提示 Claude 打开这条 Linear 工单（01:18）
- 提示 Claude 审阅这条工单，并结合代码库进行分析（01:52）
- 提示 Claude 创建一个分支并实现这些改动（02:30）
- 测试这些改动，确认它们按预期工作（02:52）
- 在 GitHub 上发起一个拉取请求（PR），把这些改动合入代码库（03:55）
- 等待工程师审阅/批准这个 PR

把镜头拉远，这套配置的真正威力就浮现出来了。诚然这是个微不足道的例子，但重点在于：一个非技术人员，现在可以靠几条给 Claude 的提示词（经由 GitHub Copilot），在 Linear 工单、代码库和工程师之间自如穿梭。

而再一次，所有这一切的关键都不在代码本身，而在于**规格说明**。

不过，要让上面这套行得通，以下几点前提很重要：

- **要具体**：用模糊的规格说明，只会得到一团乱麻的代码库。用 Claude 对工单的初稿做一次精修、审阅代码库、帮它变得更具体，是这个流程里不可或缺的一环。在我们的场景里，我们还备有一套写好规格说明的指导规范。
- **要有所取舍**：把上面这套用在较简单的任务上最理想。工单越复杂，就越需要懂行的人介入（在这些场景里，“自助”最终一点都不自助）。
- **要有把关人**：这套方法之所以能成，是因为背后有一位真正懂行的工程师在审阅改动，确保「简单」与「功能」之间的平衡不被打破。

但让我们把话说清楚：**规则已经变了。对于每个构建产品的人——包括大语言模型（LLM）在内——规格说明就是真相之源。**

有了合适的配置，一个非技术人员完全有理由期待自己能向代码库做出贡献。花上足够的时间和耐心，你甚至能开始理解代码库、自己实现改动，而不是每次都指望 Claude 来救场。

说不定有一天，你还能期待一个 AI 智能体一边替你盯着工单，一边喝你的咖啡呢。

如果你是一名 PM，正担心 AI 会对你的工作做什么，关键是意识到：**工作本身正在改变**。但这对其他每个人也都一样。好的一面是，一名优秀 PM 所需的核心技能，在这个新世界里反而更有价值了。

正如我们在上一篇文章里预测的，以这种方式运作的公司，需要的 PM 会**更多，而不是更少**。而且事实证明，这个预测正在相当不错地应验。

## 规格说明万岁！

创造了“赛博空间（cyberspace）”一词的科幻作家威廉·吉布森（William Gibson）曾说过：

> **未来已经在这里了——只是分布得还很不均匀。**

每当我想起 AI 能做到什么、不能做到什么时，就会想起这句话。今天，AI 的进展极不均衡。有些事——生成代码、文本、图像——已经实现了量子跃迁，它们以“AI 速度”运转。另一些事——与客户交谈、发现他们的需求、说服他们购买——仍然以“人类速度”运转。

这种不均衡正在重塑产品团队。聚光灯正从「实现类工作」转向「理解类工作」。那些一直让优秀 PM 脱颖而出核心技能——理解用户需求、清晰地定义问题、设计优雅的解决方案——已经变得成指数级地更有价值。

最优秀的 PM 会把这些洞察转化为规格说明——那种能让团队对齐、指导实现、并在日益自动化的开发世界里作为恒久产物留存下来的规格说明。
