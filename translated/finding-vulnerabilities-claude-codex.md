TL;DR：我们评估了 AI 编码智能体（Coding Agent）在真实代码中发现漏洞的效果。

- 方法：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行且大型的开源 Python Web 应用中寻找漏洞。它们合计产出了 400 多条安全发现，由我们的安全研究团队逐一评审。
- AI 编码智能体能找到真实漏洞：Claude Code 找到 46 个漏洞（真阳性率 TPR 14%，误报率 FPR 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。其中约 20 个是高危漏洞。
- AI 能理解上下文，却卡在数据流上：Claude Code 最擅长发现不安全的直接对象引用（Insecure Direct Object Reference，IDOR）类 bug，真阳性率（TPR）为 22%（13 个正确问题/59 个报告）；但它难以跨多个文件和函数进行污点追踪（taint tracking），对 SQL 注入的 TPR 仅 5%（2/38），对 XSS 为 16%（12/74）。OpenAI Codex 难以报告出任何正确的 IDOR，TPR 0%（0/5），在 SQL 注入 0%（0/5）和 XSS 0%（0/28）上表现极差，但出人意料地比 Claude Code 报告出更多正确的路径遍历（Path Traversal）问题，TPR 47%（8/17）。
- 非确定性是真实难题：在完全相同的代码库上多次运行完全相同的提示词，往往得到大相径庭的结果。在某个应用中，三次完全相同的运行分别产出了 3、6 和 11 条不同的发现。

要点总结：

- 使用相对简单的、以安全为核心的提示词，AI 编码智能体已经能在真实应用中找出真实漏洞。
- 但是：取决于漏洞类别，结果可能相当嘈杂（高误报率），尤其是在 SQL 注入、XSS、SSRF 这类传统的注入型漏洞类别上。
- 详细的评估与基准测试（Benchmark）是理解某种方法在发现漏洞上有多有效的关键（这一点一直成立，但在 LLM 这类非确定性工具出现后更是如此），也能帮助你判断改进是否朝着正确的方向前进。

## 关于基于 AI 的漏洞挖掘的开放研究问题

为引导我们的调查，我们把「LLM 擅长找 bug 吗？」这一宽泛问题拆解成更具体、可度量的子问题。

- 基于 LLM 的漏洞发现的误报率和漏报率是多少？它们会随编程语言、框架、代码库规模或漏洞类别而变化吗？对代码书写方式的敏感度如何？

## 常规 SAST 基准测试的问题：缺乏真实感

在深入我们的发现之前，先谈谈我们如何衡量 AI 表现。当前许多研究/主张依赖的基准测试虽然有价值，却未能充分捕捉真实世界代码的复杂性。

- 带已知漏洞的应用：这些基准测试只使用带已知漏洞的开源应用；多亏 Kinnaird McQuade，很多都能在 vulnerable-apps 中找到。如果你读过这个博客，你可能认得其中一些名字：WebGoat、JuiceShop、OWASP Benchmark 等。但这些有个问题：当前的 LLM 很可能已经摄入了这些仓库的代码，以及互联网上大量公开的解析文章，从而具备先验知识、使结果失真。它们的代码往往不真实，充斥着大量注释、标注和变量名，暗示甚至直接描述了漏洞位于代码何处或如何利用它们。有时，工具结果甚至被检入仓库中。摘自 javaspringvulny 的 SearchService.java

摘自 juiceshop，挑战本身就是文件名的一部分……

- XBOW 为自动渗透测试工具提供了基准测试，但并不适合静态分析：代码往往过于人为、过于简化，不能代表真实应用。ZeroPath 在对其进行清理方面做得不错，但只有一小部分被清理过。此外，这些测试用例每个都是微型应用，专为模拟一个专门的攻击场景而设计。若聚焦 Python 基准测试，XBOW 有 45 个；45 个不同的微型应用，平均不到 98 行代码、3 个 Python 文件。这太小了，无法捕捉在整个人代码库或众多函数间搜索与推理的复杂性。
- CVE（通用漏洞披露）记忆偏差：由于 LLM 在互联网上海量公开数据上训练，其中包括那些发现并修复了 CVE 的代码库本身。这造成了一个根本性的数据污染问题。AI 可能并非通过新颖的分析检测到漏洞，而只是识别出它在训练期间记住的模式。

最近，学术界设计了 CyberGym、Eyeballvul 或 SecVulEval 等基准测试。它们有大幅改进，也更接近真实世界案例，但要么缺乏对现代 Web 应用的关注，要么把漏洞从更广泛的应用上下文中孤立出来。

- EyeballVul：Timothée Chauvin 提出的一个较新的基准测试，它从开源项目中提取真实、经人工审核的漏洞，并将其呈现为最小化、可复现的测试用例。虽然基于真实代码，它仍把漏洞从更广泛的应用上下文中孤立出来，使搜索问题变得更容易。
- SecVulEval 与 CyberGym：这些套件用于评估 C 或 C++ 中的漏洞。虽在其领域内有价值，但它们聚焦 C 和 C++，意味着这些数据并不适用于主导现代云原生开发的 Python/JavaScript 及其他以 Web 为中心的语言。

虽然这些方法各有用途、有时应当使用，但它们未必反映现代软件开发的实际。真实世界应用不是干净、孤立的函数，而是由依赖、框架和业务逻辑构成的复杂网络。

我们的方法不同。我们在 11 个大型、基于 Python、积极维护、使用常见 Web 框架（Django、Flask、FastAPI）编写的开源项目上进行了测试。我们的方法与前述方法互补，并且我们认为其独特之处在于：a）力求代表真实世界中由 AI 驱动的漏洞发现（而非小型、孤立的合成样例）；b）未被模型训练数据污染；c）代表了大多数开发者和公司实际正在构建的应用类型——使用现代语言和框架的 Web 应用。

### 我们发现了什么

Claude Code 和 Codex 今天都很有用：它们能找到真实的安全漏洞，但非常嘈杂。总体噪声仍然很高，但它们在这些流行的开源 Python Web 应用中找到了真实的安全漏洞。总体上，Claude Code 找到 46 个漏洞（TPR 14%，FPR 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。

- 许多 IDOR bug 乍看是正确的，Claude Code 还给出了可信的修复：LLM 不仅能找到这些 bug，还能给出可信的修复，例如依据代码中已有的模式注入新的权限检查。IDOR 问题难以分诊，我们不得不对其中大多数进行测试才能确认，这使真阳性率下降了很多。
- Claude Code 是个好的安全护栏工具？许多发现虽然严格来说是误报，但仍是不错的「护栏」建议，或看起来像护栏建议。例如，模型常常建议对一条本已安全的 SQL 查询进行参数化。虽然这不算漏洞，但它强化了代码。我们仍将其视为误报，只是没其他误报那么严重。然而，这些代码加固建议并不总是可信。我们发现若干案例，尤其是在客户端 JavaScript 代码中，AI 试图修复它认为与 DOM 操作有关的问题，但实际上破坏了代码（在我们观察到的案例中是 HTML 双重转义），而那里从一开始就没有安全问题。
- XSS 与 SQL 注入——难以把各组件拼在一起：模型难以追踪数据从服务端框架到客户端组件（XSS 的常见模式）的流动，也难以穿越复杂的应用层级。它常被静态定义的数据搞糊涂，或无法识别服务端的清洗。
- 重复提示词有助于获得更多结果：LLM 的概率性质意味着，用略有不同的方式问同一个问题可能带来新发现，凸显了分析的不一致性。在同一代码库上多次重复同一提示词会给出不同答案，但最终又会绕回到相同的发现。
- OpenAI Codex 有时未能报告有效的 SARIF。我们预期的 66 份报告中有 9 份不是有效 SARIF。我们考虑了那些文件中报告的所有发现，但它们并非有效 SARIF 或 JSON。在我们尝试的所有案例中，Claude Code 都没有这个问题。

## 同样的代码、同样的 AI，每次却是不同的 bug：AI 编码智能体的非确定性难题

为探索非确定性在实践中如何体现，我们选取其中三个应用，针对同一安全问题（IDOR），用同一提示词多次运行。一个模式浮现出来：AI 的发现每次运行都不相同。

在漏洞检测的语境下，这是个重大问题。首先，作为安全工程师，理想情况下我们希望得到的保证是「我们的代码已针对重要漏洞类别被扫描过」，而不是「我希望这次模型搜索得很彻底」。

其次，间歇性地检测漏洞会在你的安全工具或漏洞管理系统中造成不一致和噪声。例如，如果你使用 SAST 平台、ASPM 或自建的某种系统，这些系统常常假定：先前检测到的某个漏洞不再出现，就说明它已被修复。但在 LLM 驱动的检测中未必如此，因为单次扫描可能漏掉它，于是后续扫描再次发现同一问题时就会生成一条「新」发现，导致重复的 JIRA 工单和开发者的沮丧。

以下是我们观察到的一些具体例子：

- PY-APP-007：第一次运行中，AI 识别出一个「搜索缺少授权」漏洞，而另外两次运行都没有。第二次运行标记出它独有的一些问题。第三次运行则发现了它自己独有的一组漏洞。
- PY-APP-006：情况类似：第一次运行挖出了用户 API 中的一个漏洞，而后续运行聚焦于代码库的不同部分，如事件摘要（event abstracts）和笔记（notes）模块。
- PY-APP-002：这里的可变性或许最为显著。识别出的漏洞数量从第一次运行的 3 个跳到第二次的 6 个，再到 11 个。每次运行给出的发现只有部分重叠。

那么，背后原因是什么？我们认为关键因素是所谓的上下文腐化（context rot）与压缩（compaction）。当 AI 智能体被要求分析整个代码库时，它要处理海量信息：上下文腐化导致它无法从自身上下文中准确检索。为应对这一点，LLM 使用一种有损压缩（有时称为 compaction），这意味着函数名、路径等更细的推理细节可能在摘要过程中丢失。

把它想象成试着概括一部又长又复杂的小说。你会抓住主要情节点，但必然会漏掉一些微妙与细节。同样，AI 可能丢失对某个特定架构模式或某条细微数据流的追踪，导致它在一次运行中漏掉某漏洞，而在另一次运行中却抓到它。我们在 PY-APP-006 中看到一个清晰的例子：AI 提出的某个修复不完整，因为它未能复用一个用于用户授权的现有基类——这段关键的上下文仿佛在那次特定运行中丢失了。

这种非确定性对我们如何对待原生 AI 的 SAST 有重大影响。一方面，AI 每次「思考」方式不同的能力意味着它能探索更广泛的潜在攻击向量，就像一支视角多样的人类渗透测试团队。另一方面，它引入了一定程度的不确定性，可能导致困惑或异常行为。

- 覆盖不完整：单次运行可能带来虚假的安全感，因为它可能漏掉后续运行才能抓到的关键漏洞。
- 缺乏可重复性：无法复现结果使得验证 AI 的发现、以一致且可重复的方式信任其输出变得困难。
- 成本与时间增加：为获得更完整的图景而需要运行多次审计，会显著增加所需的时间和计算资源。注意：对于传统软件，一旦写好，你基本可以「免费」再次运行它（除硬件成本、电费等）。对重度依赖 LLM 的工具则不然，在这类情况下，读入一个代码库并对其推理，每次扫描可能产生数十到数百美元的令牌（token）成本。对当今的模型而言，这一成本可能随时间下降，但更新的模型可能更昂贵。

## Claude Code 新的 /security-review 命令有多有效？

Anthropic 为 Claude Code 发布了一个新命令，名为 /security-review。它设计用于在拉取请求（PR）上运行，检查被更改的文件并通过提问来识别具体安全问题。你可以在这里找到该提示词。

当我们在整个代码库上运行这个命令时，我们发现它识别出的安全问题相当有限。很多时候，它找不到我们让 Claude Code 一次只搜索某一特定安全问题时所得到的那些安全问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了这个命令，它在所有这些中只找到一个 XSS，这与我们在整体实验中得到的结果大相径庭。

## 回答我们的问题

让我们基于所学，回顾最初的研究问题。

- 误报/漏报率是多少？对于真实世界代码上的原始 AI 而言，误报率非常高：最好的情况是 Codex 路径遍历 53% 或 Claude Code IDOR 78%，最差的情况是 Claude Code SQL 注入 95%、Codex SQL 注入或 IDOR 100%。不同应用间的表现也差异巨大，从 PY-APP-002（Claude Code）100%（10/10）的真实 IDOR，到 PY-APP-007 的 0%（0/7）。跨所有应用和所有报告的 issue，Claude Code 找到 46 个漏洞（TPR 14%，FPR 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。由于我们使用的是真实应用，在这次实验中我们无法准确衡量漏报。我们会在即将发布的博客中介绍衡量漏报率的技术！
- 它为什么会失败？我们观察到的主要弱点是缺乏对注入类问题所涉代码执行的深层语义理解。模型难以处理过程间污点流和隐式流，而这正是传统 SAST 引擎通常擅长的地方。部分局限也来自上下文压缩与上下文腐化。我们将继续更详细地探索这些局限，并探索缓解它们的方案。
- 脚手架与智能体化工作流有多重要？它们不仅重要，而且正变得必不可少。AI 在安全评审中的未来不是单个庞大的模型，而是一套能使用工具、对证据进行推理并协作发现与验证漏洞的 AI 智能体系统（包括像我们案例中的编码智能体）。虽然我们（目前）还没有关于「使用能访问 Claude Code 的智能体」与「用更典型的上下文工程（即搭建脚手架以提供所有相关代码）加推理模型」之间差异的数据，但我们观察到系统在走完一个复杂流程、并在此过程中就报告安全问题做出有依据决策的能力上存在巨大差异。话虽如此，一个反例是 Sean Heelan 如何通过足够的上下文工程让一个推理模型报告出一个漏洞（8% 的情况下）。我们强烈建议你读一读他的博客。
- 这一切的成本如何？遗憾的是，我们未能一致地追踪 Claude Code 和 Codex 之间的成本。Claude Code 的总成本为 114 美元，涵盖所有这些漏洞和所有这些应用（不含非确定性测试和 /security-review 命令的运行）。

## 数据集：未来发布

我们今天不会发布数据集，也不会发布所分析开源应用的名称，因为我们正处于负责任披露的过程中，正在联系应用开发者以修复并验证所有安全问题。完成后，我们就会放心地发布这些数据。

## 结论

LLM 并非明天就能取代人类安全工程师的银弹，事实上，它们在端到端发现高危注入型漏洞方面相当薄弱。然而，它们是一件极其强大的工具。我们的研究表明，通过理解它们的优势（上下文推理）与弱点（代码的深层语义），并借助先进的静态分析引擎在其周围构建精密的智能体系统，我们能够创造出一代远比以往任何东西都强大的安全工具。
