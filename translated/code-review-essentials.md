# 软件团队的代码评审要点（Code Review Essentials for Software Teams）

> 作者：Blake Smith（Sprout Social 首席软件工程师）
> 原文日期：2015 年 2 月 9 日

代码评审（Code Review）是任何协作式软件项目中不可或缺的一环。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套稳健的流程，让团队成员以及代码库本身都始终朝着正确的方向前进。

代码评审是一个强大的工具，它能够：

- 帮助团队成员随着系统的变化持续更新他们对系统的心智模型（mental model）
- 确保改动正确地解决了问题
- 为设计方案的优劣展开讨论
- 在 bug 进入生产环境之前将其捕获
- 保持代码风格与组织结构的一致性

把这些收益看作一个「需求层次」会很有帮助。

## 让团队成员保持同步

代码评审最核心的作用，是让团队的每一位成员都朝着正确的方向前进。你无法安全地改动一个你不理解的系统，而代码评审能让团队在认知上保持一致。当 Bob 为「会计子系统」提交一个拉取请求（Pull Request，PR）时，Amy 在评审 Bob 的代码过程中，会同步更新她对该系统的心智模型。Amy 有机会就她看不懂的地方提问，Bob 则既能借此厘清自己的设计决策，也能向他人讲解自己的工作。一个月后，当 Amy 需要改动会计子系统时，她的心智模型已经是最新状态、可以立即上手。她会花更少的时间去读代码、在脑子里拼凑系统全貌，而把更多时间花在思考更高层的抽象与设计上。所有人都受益，因为所有人都保持同步。

## 做好一个 Pull Request

在你动手写第一行改动代码之前，先问自己以下几个问题：

- 「这件事是不是当前最该做的？」来自客户、内部团队成员以及其他相关方的需求总是相互竞争。在你一头扎进去之前，先这样问一问，能帮你把优先级理清。其他流程，比如迭代 / 冲刺（sprint）计划会议，也有助于让这件事保持在正轨上。
- 「团队是否已经就该改动的正确性达成共识？」如果没有，最好先通过邮件或当面发起一场设计讨论。当大家在改动之前就设计方案达成一致时，你的改动被接受的概率会更高。
- 「我该如何把这个改动拆分成易于评审和理解的、可消化的小块？」小改动更容易思考、更容易理解。只有团队能快速领会你的改动，好的讨论才会随之而来。如果你的改动过于庞大，队友们只会两眼发直，最后你得到的可能只有几条关于风格的小挑剔。
- 「我打算如何测试这个改动，以消除 bug 并保证正确性？」你可能有一个 QA（质量保证）部门，但交付高质量、可运行的软件依然是开发者自己的职责。易于测试的软件通常耦合度更低、被拆成更小的块，也更容易推理。你需要为所有改动都准备一份测试计划。

我发现，提前回答这些问题从长远看帮我省去了大量麻烦。你最不想看到的就是：花好几天写出一个改动，结果却因为根本性的设计缺陷或团队分歧而被否决；或者你的改动因为没人能验证其正确性而被搁置。再次强调，目标是在改动系统的同时，让其他团队成员对你的改动保持同步。提前问自己「如何把工作拆成小块」以及「如何测试这些小块」，在很多方面都有帮助：

- 它降低了风险
- 它让改动更容易被推理
- 它推动你走向更好的设计

你宁愿用手术刀做许多次小而精准的切割，也不愿用砍刀来一次巨大的劈砍。在大多数「新增型」的场景下，我更偏好「手术刀式开发」，把砍刀留到需要删除大段死代码的时候再用。

## 发送 Pull Request

好，你已经获得了团队的认可、确认改动方向正确，并且完成了你最初设定的设计。那么，真正发送这个 pull request 最有效的方式是什么？你在这些改动上付出了很多努力，希望团队的其他成员能关注你的 pull request 并尽快给出反馈。你该怎么做？

还记得我之前说过，代码评审最重要的一点是让团队的集体心智模型保持良好对齐吗？你的其他队友很可能在做一件与你完全不同的事，甚至是在系统中完全不同的另一部分。他们的大脑处于完全不同的上下文里，所以你必须通过给他们提供做评审所需的、有帮助的指引来克服这一点。这意味着要写一份组织良好的描述：你做了哪些改动、为什么做这些改动，以及任何仅靠读代码无法获得的、其他相关信息。不要让队友做超出必要的脑力劳动。

我们来看几个 pull request 描述的好坏示例。

**反面示例：**

> 标题：修复未初始化内存的 bug
> 描述：
>
> 这就是之前我和 Bob 讨论过的那个 bug。我在编译器上遇到点麻烦，但总算把它搞定了。大家看看有什么意见。

如果你是这份 pull request 的开发者，请停下来，设身处地站在代码评审者的角度想一想。这个标题含糊不清，引出的问题比给出的答案还多：内存 bug 在哪里？这个改动的严重程度如何？之前你和 Bob 讨论的那个 bug 到底是什么？你在编译器上遇到了什么麻烦？这份描述既没有提供任何关于问题本身的有用上下文，也没有对你的改动给出任何有帮助的说明。如果这份 pull request 很长，评审者就不得不在还没来得及思考「这个改动如何融入系统的整体设计」之前，就先钻进代码里，在脑子里做一番体操来获取上下文。

下面是经过改进、有助于厘清这个变更集（changeset）的示例：

> 标题：修复因未初始化内存导致的启动时进程崩溃 [#54633]
> 描述：
>
> 这个 bug 由于我们的统计 Counter 类中的内存初始化错误，导致进程在启动时崩溃。我和 Bob 讨论过这件事，我们都认为这些崩溃属于罕见的边缘情况，不值得为此发布一个热修复（hot-fix）版本。下面是改动摘要：
>
> - 将底层的 int 变量移入类的初始化器，以避免 Counter 中出现未初始化内存。
> - 重构了 Counter 接口，简化了调用方的条件逻辑，并防止进一步的「差一」计数问题。
> - 新增一个能暴露该崩溃的单元测试。
>
> 测试：我已确认测试套件仍然通过，并手动验证了该崩溃在本机不会再发生。

这份 pull request 描述在几个方面有所改进：标题的描述性足够强，能快速给评审者一点上下文，并吸引他们点开邮件进一步了解。评审者知道这是一次进程崩溃（这通常是非常糟糕的事），而且还有一个 bug 报告编号，感兴趣的评审者可以去查看该 bug 报告的更多细节。新的描述还说明了问题发生的位置，并帮助传达了这次修复的严重程度。描述里有一份摘要，列出了 pull request 中的高层结构性改动，让评审者在看代码之前就能对改动形成一幅整体图景。代码评审者不应该对看到的内容感到意外。这个示例还列出了所执行的测试，这会给评审者信心：这些改动经过了深思熟虑、充分测试、可以合并了。让你的评审者轻松到「傻瓜式一键点合并」，就是为他们的成功铺路。

## 评审者：如何给出建设性反馈

评审流程中接下来要考虑的，是向同事给出建设性反馈。如果目标是清晰与对齐，那么高质量的、建设性的反馈能帮助每个人更好地理解系统，并推动代码变得更好。

避免说这样的话：

- 「这个设计是坏的。」它为什么是坏的？怎样才能改进？这样的表述会打击信心，还可能伤到自尊。
- 「我不喜欢这个改动。」你为什么不喜欢？你希望换成什么？不喜欢某样东西是允许的，但你应该表达出你的想法，并就代码如何改进提供有用的线索。
- 「你能把它重写得更清晰吗？」我现在这样写有什么问题？我该怎么重写？哪里不清晰？这样的评论本身就很不清晰，也没有给出明确的改进方向。

相反，可以这样说：

- 「这段代码如何处理负整数？」这种反馈很具体，能让开发者自己去把各种结果想一遍。作为评审者，你可能知道这段代码在处理负整数时会崩溃，但更好的做法是让开发者自己领悟到这一点。这类提问也可能暴露出测试的缺口，或对范围做进一步说明的需求。
- 「这段我有点看不懂，我不明白为什么 A 类要和 B 类打交道。」如果开发者没有提供有用的描述，代码结构也不够整洁，这类评论有助于推动设计的清晰和代码的整洁。
- 「看起来你在这里打破了一个接口边界。这会对用户产生什么影响？」你指出了你注意到的一个问题，同时默认对方是有意为之、给予其怀疑的余地。这样他们就能想清楚打破接口边界所带来的、不易察觉的后果，要么为自己的决策给出理由，要么选择改掉它。

总的来说，把反馈组织成问题，是推动清晰与正确性的好办法，同时还能帮助开发者改进他们未来的设计。这通常也是高质量的创意写作小组互相给反馈的方式。在创意写作的语境下，说「我不喜欢这个角色」是有害的，而同样的评论可以被更清晰地重新表述为：「在第一章里，你的角色温暖而富有同情心，现在却变得冷漠而冰冷，在我看来他不再像个真实的人了。」这样就有了具体的反馈，可以进一步澄清、找出问题所在。

程序员天生喜欢解决问题、指出问题，所以他们天生就喜欢发现并指出缺陷。把代码评审当作「通过挑出同事代码里的毛病来证明自己多聪明」的机会，是很诱人的。别这么做。代码评审是让更多双眼睛审视一个改动、找出关键问题的方式，但你的目标应该是：在解决眼前问题的同时，以一种能鼓励团队成员提升技能的方式去评审。

## 风格要点

花括号的位置、变量 / 函数命名、缩进和空格问题都应该处理，但它们不是优质代码评审的核心目的（请注意，我把它们放在了代码评审金字塔的顶端）。如果你发现你的团队把 90% 的时间都花在纠结缩进和变量命名上，那么你很可能是把大家的时间浪费在那些大体上可以被自动化的事情上了。写一份风格指南，在代码提交（check-in）时强制缩进和空格规则，然后把时间花在更有价值的问题上。我并不是要贬低统一风格的重要性。恰恰相反，拥有一套一致且符合语言习惯的风格，是让代码库易读、易理解的最简单方法之一。但如果你的整个代码评审都围着这些简单任务打转，就该问问自己：你是不是在回避那件更难、也更重要的事——让团队保持心智对齐、思考更高层的设计。
