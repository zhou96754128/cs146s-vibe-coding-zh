# SAST vs. DAST vs. RASP：应用安全测试方法对比

Learn 2024年12月18日 Shanika Wickramasinghe

到 2025 年，全球信息安全支出预计将达到 2120 亿美元。这意味着相较 2024 年增长 15%。根据 Gartner 的说法，生成式 AI 的兴起和云的采用是这一快速增长的关键原因。该分析机构进一步预测，到 2027 年，GenAI 将参与 17% 的网络攻击。

企业需要超越传统方法的先进安全策略，以应对这些日益增长的威胁。因此，企业主需要了解 SAST、DAST 和 RASP 等安全解决方案，因为它们能为应用提供多层防护。

（相关阅读：应用安全详解与常见软件测试方法。）

## 什么是 SAST？

静态应用安全测试（Static Application Security Testing，SAST）是一种白盒安全测试方法。SAST 使用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具在应用未运行时对其代码进行分析。

开发者使用 SAST 来检测各类安全风险，例如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出，以及代码中其他 OWASP 漏洞。由于 SAST 单独无法识别运行时特有的漏洞，开发者往往必须将 SAST 与其他测试方法结合，才能实现全面的安全。

SAST 是软件开发生命周期的重要组成部分，因为它能及早发现漏洞。发现得越早，修复成本越低。由于 SAST 工具可在开发阶段执行，开发者如今能够在产品发布到市场之前，编写并测试代码多达一千次（!!）。

SAST 可以集成到 CI/CD（持续集成 / 持续交付）流水线中，这样做时被称为“安全 DevOps”或“DevSecOps”。SAST 通过自动化具备很强的可扩展性。实施覆盖 SAST 技术的自动化测试，使其成为快速应对代码层面风险的高效方案。

## 什么是 DAST？

动态应用安全测试（Dynamic Application Security Testing，DAST）是一种黑盒测试方法。DAST 中的“动态”（Dynamic）一词表明，该方法在应用运行时评估其安全性。与 SAST 不同，DAST 不需要访问应用的源代码。相反，它会：

- 模拟外部攻击者的行为。

- 从外部测试应用，以识别仅在运行时才会出现的漏洞。

DAST 能够识别各种安全缺陷，例如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模仿真实世界的攻击场景，DAST 工具评估应用对这些模拟威胁的响应方式。借助这种方法，开发者可以识别静态测试方法（如 SAST）可能遗漏的弱点。

通常，开发者在软件开发生命周期的后期阶段执行 DAST，往往就在部署之前。通过在应用的实时环境中进行测试，DAST 能清晰呈现运行时安全的全貌，并支撑性能更佳、能抵御潜在攻击的应用。

## SAST 如何工作？

开发者使用 SAST 工具施加预定义规则和其他检测方法——例如模式匹配和数据流分析——来识别编码错误及其他漏洞。他们将这些工具集成到 IDE 或 CI/CD 流水线中，以在编码和测试阶段自动执行扫描。

### 常见的 SAST 方法

以下是 SAST 中使用的一些方法。

模式匹配会扫描代码库，查找已知的不安全编码实践模式。例如，使用弱加密算法或不安全的 API 调用。

数据流 C 追踪数据如何在应用中流动。通过追踪不可信输入路径到敏感操作，它可以识别 SQL 注入或缓冲区溢出等漏洞。

控制流分析可以分析应用的控制结构。例如循环和条件分支，以发现逻辑缺陷或竞态条件等潜在漏洞。

自定义规则创建。许多工具允许开发者创建自定义规则以落实编码最佳实践。以下是这些自定义规则的一些示例：

- 标记 SQL 查询中任何使用未净化输入的情况。

- 识别将用户提供的数据输出到浏览器时未正确转义的代码。

- 标出使用有漏洞或已弃用函数的情况，例如 JavaScript 中的 eval() 或 C 中的 strcpy()。

- 检测源代码中出现的硬编码 API 密钥和密码，并标记任何对用户提供数据缺少输入验证的实例。

依赖扫描。一些 SAST 工具会分析应用中使用的第三方库和框架，以识别依赖中的漏洞。

语义分析。通过解读代码的含义而非仅其结构，SAST 工具可以检测不安全的配置或 API 的误用。

机器学习模型：先进的 SAST 工具纳入机器学习算法，通过分析大规模数据集中的模式来识别此前未知的漏洞。

### 使用 SAST 工具时的性能考量

SAST 工具通常需要大量 CPU 和内存资源。在分析大型代码库时，这可能是个主要问题。对一百万行代码进行完整扫描可能会消耗数 GB 的 RAM。

SAST 扫描所需的时间会随代码库规模大幅变化，小型项目可能只需几分钟，而企业级应用则可能长达数小时。这会影响：

- 构建流水线的时间线

- 开发者生产力

可考虑使用支持增量扫描的现代 SAST 工具，让你只分析变更过的代码，而不是整个代码库。

此外，通过规则选择和范围界定进行性能调优至关重要。配置不当的 SAST 工具会不必要地分析非关键代码路径，浪费时间和资源却无法带来安全收益。

## DAST 如何工作？

DAST 工具模拟真实世界的攻击——例如，将各种形式的恶意数据发送到输入字段，观察应用如何处理它——以识别应用行为和响应中的漏洞与弱点。

### DAST 的步骤

该过程通常包含以下步骤。

第 1 步：扫描。扫描 Web 应用以发现入口点（如 URL、表单和 API）。此步骤会摸清应用的结构并识别潜在攻击面。

第 2 步：攻击模拟。通过向应用发送精心构造的请求来模拟恶意活动。这些请求尝试利用入口点，以测试跨站脚本和跨站请求伪造等漏洞。

第 3 步：漏洞检测。分析应用的响应以识别安全弱点。它会评估应用在攻击下是否按预期运行。例如，可以注入恶意数据来检测 SQL 注入缺陷。

第 4 步：报告。生成包含所检测漏洞和修复建议的报告。开发者可以利用报告中的结果来修复已识别的问题。

现代 DAST 解决方案可以纳入 AI 驱动分析和实时数据集成等高级功能。它们会自动创建测试集，动态适应应用的结构，并利用机器学习算法将误报降至最低。

### 使用 DAST 工具时的性能考量

以下是使用 DAST 工具时需要牢记的一些性能瓶颈。

- DAST 工具会主动与运行中的应用交互，暂时提高应用和 Web 服务器上的 CPU 和内存使用率。

- DAST 扫描期间产生的大量并发请求会消耗可观的网络带宽。

- DAST 扫描器往往会通过生成唯一请求来绕过或使应用缓存失效，从而降低缓存机制的有效性。

- DAST 工具创建和管理多个测试会话会增加应用服务器上的内存使用。

为避免此类问题或尽可能减轻其影响，请遵循以下做法。

- 在应用使用量最少的非高峰时段安排 DAST 扫描。

- 在镜像生产环境的预发布或准生产环境中进行扫描。

- 使用 DAST 工具中的限流功能来控制并发请求数量。

- 在扫描期间增加应用服务器的线程池。

- 为 DAST 扫描器 IP 配置单独的缓存策略。

- 如果超出性能阈值，则实施自动暂停扫描。

## SAST vs. DAST：关键区别

下表总结了 SAST 与 DAST 之间的区别。

| 标准 | SAST | DAST |
|---|---|---|
| 测试类型 | 白盒测试。可在访问源代码的情况下，从内到外测试应用。 | 黑盒测试。无法访问源代码，从外部测试应用。 |
| 支持的软件类型 | 支持多种类型的软件，包括 Web 应用、Web 服务和厚客户端。 | 支持 Web 应用和 Web 服务，但通常不支持其他软件类型。 |
| 在 SDLC 中的阶段 | 在软件开发生命周期早期执行。 | 在 SDLC 后期进行，往往在部署期间或之后。 |
| 检测到的漏洞 | 识别编码缺陷，例如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。 | 检测运行时问题，例如服务器配置错误、拒绝服务漏洞和应用层缺陷。 |
| 修复漏洞的成本 | 较低，因为问题在 SDLC 早期就被识别。 | 较高，因为漏洞发现得较晚，往往需要紧急修复才能按时部署。 |
| 运行时与环境问题 | 无法检测运行时特有或环境相关的漏洞。 | 可以识别仅在运行时出现或因环境因素而出现的漏洞。 |
| 深度 vs. 广度 | 深入洞察代码层面的漏洞。 | 提供应用外部安全风险的全局视图。 |
| 与工具集成 | 可与 IDE 和 CI/CD 流水线集成，实现自动化静态分析。 | 可与 CI/CD 流水线集成，实现持续的运行时测试。 |
| 误报与漏报 | 由于深入的代码分析，误报概率更高。 | 误报较少，但由于内部可见性有限，漏报风险更高。 |
| 技术依赖 | 依赖编程语言和框架；需要与工具兼容。 | 独立于应用框架，因为它们从外部与应用交互。 |

## SAST 与 DAST 的优缺点

### SAST 的优点

- 在软件开发生命周期早期识别安全漏洞。

- 分析代码库，包括基本函数和复杂分支。

- 直接在源代码上运行，无需应用运行。

- 提供实时反馈和全面的洞察，例如漏洞的确切位置。

- 生成可通过仪表板跟踪的可导出报告。

- 支持自动化，因此比人工代码评审更快、更高效。

### SAST 的缺点

- 往往会产生大量误报。因此可能需要人工评审。

- 无法识别运行时或环境特有的漏洞，例如配置错误。

- 需要针对每种编程语言的特定工具，因此维护复杂。

- 难以理解外部库、API 和 REST 端点。

### DAST 的优点

- 识别仅在应用执行期间出现的漏洞。

- 从外部运行，无需访问源代码。这对于测试第三方应用或已编译代码很有效。

- 模拟实际攻击场景，识别 SAST 遗漏的风险。

- 独立于应用的编程语言运行。

- 评估整个应用和系统。这包括内存消耗、资源使用和第三方接口。

### DAST 的缺点

- 仅关注应用的外层，可能遗漏更深层的漏洞。

- 在 SDLC 后期应用，因此修复更昂贵、更耗时。

- 会遗漏 SAST 工具可通过源代码分析识别的某些漏洞。举例来说，假设一个 Web 应用使用不安全的随机数生成器（例如 JavaScript 中的 Math.random()）来创建会话令牌。DAST 可能会遗漏这一缺陷，因为它只测试运行时行为。（但 SAST 可以检测到它。）

- 大型项目需要自定义基础设施，并需要运行多个应用实例以并行处理，因此资源消耗大。

## 我应该在何时使用 SAST、何时使用 DAST？

SAST 和 DAST 在保障 SDLC 安全方面扮演互补的角色。理解各自的适用时机有助于实现全面的安全覆盖。

### 何时使用 SAST

在早期开发阶段。开发者使用 SAST 在 SDLC 早期识别 SQL 注入和硬编码凭据等漏洞。通过在部署前捕获这些问题，他们降低了修复的成本和复杂度。

例如：一个 SAST 工具扫描 Python 代码，标记出源代码中嵌入了硬编码 API 密钥的漏洞。开发者重构代码，改用环境变量来安全地存储和读取密钥。

用于代码评审。SAST 集成到版本控制系统中，让开发者在提交代码之前进行扫描。这确保只有安全的代码进入代码仓库。

示例：SAST 工具可以检测到直接利用用户输入构造文件路径而未经验证的漏洞，这会使应用暴露于路径遍历攻击。开发者通过净化输入并使用安全的库函数处理文件路径来修复该问题。

在持续集成/持续部署流水线中。SAST 在 CI/CD 过程中运行自动化扫描。它为开发者提供实时反馈。

### 何时使用 DAST

预生产测试。开发者使用 DAST 在预发布或 QA 环境中识别运行时漏洞（例如：不安全配置、认证缺陷、访问控制不足）。

示例：DAST 工具可以检测出暴露敏感数据的数据库配置错误。随后开发者可以在部署前加固该配置。

在部署后监控中。DAST 工具持续扫描已部署的应用，以发现由环境变化或新兴威胁导致的漏洞。这保证应用随时间推移始终保持安全。

测试第三方集成。DAST 可以模拟外部攻击者的视角，以识别第三方 API 或互联系统中的漏洞。

例如：一个 DAST 工具测试某个 Web 应用时，发现第三方支付 API 中存在漏洞，信用卡详细信息通过未加密的 HTTP 连接传输。开发者通过为所有 API 通信强制使用 HTTPS 来解决该问题。

## 哪个更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：

- SDLC 阶段

- 所针对的漏洞类型

SAST 在早期开发中效果最佳，主要用于识别源代码中的漏洞、降低成本并推广安全编码实践。相比之下，DAST 关注预生产或已部署应用中的运行时漏洞。它提供关于配置错误和不安全集成等问题的洞察。

### 采用混合方法

与其二选一，不如将 SAST 和 DAST 结合，构建多层安全策略，同时应对静态代码和运行时环境中的漏洞。SAST 可以集成到早期开发阶段，在应用编译之前检测并修复代码层面的问题。一旦应用在测试环境中运行，DAST 就能识别运行时漏洞并评估应用在攻击条件下的行为。

在 CI/CD 流水线中自动化 SAST 和 DAST 扫描，可以提供持续反馈并在不牺牲安全性的前提下加速开发过程。

对于敏捷或 DevOps 环境，加入 IAST 或 RASP 等工具可以进一步增强安全性。通过关联 SAST 和 DAST 的结果，组织可以实现更全面、更有效的漏洞管理。

### 用 RASP 作为 SAST 和 DAST 的替代方案

运行时应用自我保护（Runtime Application Self-Protection，RASP）是一种直接安装在应用所运行服务器上的高级安全解决方案。

RASP 将自身嵌入应用的运行时环境。这种集成让 RASP 能够分析应用的逻辑和数据。在分析过程中，它可以：

- 在异常行为发生时将其检测出来。

- 立即阻断恶意活动。

一个关键区别是，RASP 不只是对潜在问题发出警报——它通过隔离和化解威胁主动阻止攻击，而不依赖外部工具。

RASP 为 SAST 和 DAST 提供了一种动态替代方案。与分析静态代码的 SAST 和模拟外部攻击的 DAST 不同，RASP 实时运行。它在执行期间监控应用的行为，并通过终止会话或通知防御者来响应实时威胁。

RASP 在保护应用免受绕过网络防御或在开发期间被遗漏的漏洞方面尤为有效。

然而，对 RASP 过度自信可能导致组织忽视安全编码实践。此外，RASP 可能影响应用性能，因为它直接在应用的运行时环境中运行。RASP 无法取代修复底层缺陷的必要性，但它能在修复进行期间提供持续保护。

正如一位 RASP 用户所评论的：

“是否使用 RASP 工具的决定，应基于对应用具体需求和风险状况的全面评估。”

## 未来是以 SAST、DAST 和 RASP 进行 AppSec 测试

应用测试的未来在于将 SAST、DAST 和 RASP 结合起来，构建全面的安全策略。随着安全挑战日益增长，将这些工具集成到 CI/CD 流水线并自动化其流程将变得至关重要。

AI 和机器学习的进步将使测试更高效，因为它有助于减少误报并改进威胁检测。

### 金融与金融服务行业

在金融领域，AI 驱动的工具将改变漏洞被检测和缓解的方式。SAST 和 DAST 将继续在开发和预生产期间识别编码缺陷和运行时问题。

但不会止步于此：RASP 将更进一步，利用 AI 监控实时交易。例如，RASP 可以检测到异常模式（例如：攻击者尝试实时利用某个漏洞）并阻断这些活动，同时通知安全团队。

### IoT、边缘和联网设备

就 IoT 而言，这些工具的组合将在保障联网设备安全方面发挥重要作用。具体如下：

- SAST 可以在开发期间确认固件不含漏洞。

- DAST 可以测试设备之间通信协议的安全性。

- 与此同时，RASP 监控已部署的设备，检测并阻止由新兴威胁导致的未授权访问尝试或数据泄露。

同样，使用多种方法将帮助 IoT 生态系统保持韧性。正如我们的众多示例所说明的，SAST、DAST 和 RASP 共同承诺了一个未来：应用以更强、更主动的安全措施来构建和部署。

## 韧性安全始于主动测试

将 SAST、DAST 和 RASP 结合起来，可以提供覆盖整个软件开发生命周期的稳健安全。

通过将这些方法集成到 CI/CD 流水线并利用 AI 的进步，组织可以主动响应新兴威胁。这些方法共同提供了一套整体方案，保护现代应用免受安全漏洞之害。
