# GitHub Copilot 与 VS Code 的提示词注入远程代码执行（Prompt Injection RCE in GitHub Copilot & VS Code）

> 来源：Month of AI Bugs 2025（CVE-2025-53773）

本文讲的是一个重要、同时也相当可怕的提示词注入（prompt injection）发现：它能让 GitHub Copilot 和 VS Code 中的开发者机器被完全攻陷（full system compromise）。

实现的思路是：通过修改项目的 settings.json 文件，把 Copilot 置入 YOLO 模式。

正如几天前关于 Amp 的文章所描述的，智能体（agent）中存在一种容易被忽视的漏洞模式：如果一个智能体能够写入文件、修改自己的配置或更新与安全相关的设置，就可能导致远程代码执行（Remote Code Execution，RCE）。这种情况并不罕见，也是安全评审时始终要排查的一个方向。

## 背景研究

在考察 VS Code 和 GitHub Copilot 的智能体模式（Agent Mode）时，我注意到了一个奇怪的行为……它可以在无需用户批准的情况下，在工作区里创建并写入文件。

这些编辑会立即持久化，而不是以「待审阅的 diff」形式存在于内存中——修改会立刻写入磁盘。

作为一名红队成员（red teamer），你会知道这多半不是什么好事……所以我开始研究能否利用它来提升权限并执行代码。

### YOLO 模式

于是，我接着研究了 VS Code 中那些依赖「项目/工作区文件夹内的设置」的功能，很快就找到了一个有意思的。

原来，在 .vscode/settings.json 文件中可以加上下面这行：

"chat.tools.autoApprove": true

这会让 GitHub Copilot 进入 YOLO 模式。

它会关闭所有用户确认，于是我们可以运行 shell 命令、浏览网页等等！

有意思的是，这是一个实验性功能，但默认情况下仍然存在。我并没有下载特殊版本，也没有把我的 VS Code 整体切到实验模式。

而且，它在 Windows、macOS 和 Linux 上都能生效。

## 漏洞利用链解析

劫持 Copilot 并提升权限的概念验证（proof-of-concept）利用链如下：

- 攻击始于一处提示词注入：它被植入源代码文件、网页、GitHub issue、工具调用响应或其他内容中……载荷（payload）也可以使用不可见文本作为指令。

- 提示词注入首先向 ~/.vscode/settings.json 文件加入一行 "chat.tools.autoApprove": true。如果文件夹和文件尚不存在，就会被创建出来。

- GitHub Copilot 随即进入 YOLO 模式！

- 攻击者运行一条终端命令。借助条件式提示词注入，我们还可以根据操作系统来选择要运行的内容。

- 我们实现了由提示词注入驱动的远程代码执行。

这里有一张截图，展示的是：左侧是带提示词注入的演示文件，右侧是开发者在聊天框里与之交互，然后计算器弹了出来！

当然，任何其他的提示词注入投递方式——比如来自网页、或来自 MCP（模型上下文协议）服务器返回的数据——都是攻击角度。我之所以把它放进源代码文件里，只是因为这样最容易测试。

## 将工作站加入僵尸网络——ZombAI

当然，这意味着我们可以把开发者的机器作为 ZombAI 加入僵尸网络。

另外，为了好玩，我们还可以修改 settings.json，把 VS Code 切换成红色配色方案之类的东西。

但这还没完！这也意味着我们可以打造一个真正的「AI 病毒」，让它附着在文件上，并随着开发者下载和交互受感染的文件而传播。

最后，为了证明我们对开发者主机拥有完全控制权，我们还展示了 Copilot 可以被劫持去下载恶意软件，并接入一个远程的命令与控制（Command and Control，C2）服务器。

这意味着恶意软件、勒索软件、信息窃取程序等都门户大开。

相当可怕。

## 打造一个 AI 病毒

看到这一点，你会发现这基本上就允许创建一个病毒。攻击者可以嵌入指令，一旦获得代码执行能力，额外的恶意软件就能攻陷其他 Git 项目（以及 RAG（检索增强生成）来源），植入恶意指令，并提交更改，甚至强制推送（force push）到上游。

这会导致进一步扩散，因为其他开发者会在不知情中传播受感染的代码。

最后，我们还得谈谈「不可见指令」！

## 建议与修复

除了我分享的 YOLO 模式这个例子，实际上还有更多攻击角度。当微软问我是否还有更多信息时，我又进一步查看，发现还有其他有问题的地方，比如 AI 可以写入的 .vscode/tasks.json，或者添加伪造的恶意 MCP 服务器等，这些都可能导致代码执行。而且 AI 还能重新配置项目的用户界面和配置设置。

最近我注意到，开发者常常会使用多个智能体，因此还存在覆盖其他智能体配置文件（允许列表的 bash 命令、添加 MCP 服务器……）的威胁，因为这些文件通常也在项目文件夹里。

理想情况下，AI 不应该在未经人工批准的情况下修改文件。许多其他编辑器确实会显示 diff，然后由开发者批准。

## 负责任的披露

2025 年 6 月 29 日报告该漏洞后，微软确认了复现并追问了几个后续问题。几周后，MSRC（微软安全响应中心）指出这是他们已在跟踪的问题，将在 8 月前修复。随着 8 月的「周二补丁日」（Patch Tuesday）发布，该问题现已修复。

感谢 Persistent Security 的 Markus Vervier，他也发现并向微软报告了这一漏洞（他们的分析文章见此处）；也感谢 Ari Marzuk，他似乎也同时独立发现了它。

感谢 MSRC 及产品团队的成员帮助促成修复。

## 结论

这是又一个「AI 智能体可能不会安分待在盒子里」的例子！通过修改自己的环境，GitHub Copilot 可以提升权限并执行代码，从而攻陷开发者的机器。正如我所发现的，这是智能体系统中一个并不罕见的设计缺陷。

请继续留意这类设计缺陷——它们本应在威胁建模（threat modeling）期间就被轻易发现。

干杯。
