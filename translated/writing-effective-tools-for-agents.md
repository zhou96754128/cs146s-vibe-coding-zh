# 为智能体编写高效工具——用智能体来写
发布于 2025 年 9 月 11 日

智能体的效能，取决于我们交给它的工具。本文分享如何编写高质量的工具与评测，以及如何借助 Claude 为它自己优化工具，从而提升性能。

模型上下文协议（Model Context Protocol，MCP）可以让 LLM（大语言模型）智能体拥有多达数百个工具来解决真实世界的问题。但我们要怎么做，才能让这些工具发挥最大效力？

在本文中，我们介绍了一些最有效的技巧，用于提升各类智能体化 AI 系统¹ 的性能。

我们先讲如何：
 - 搭建并测试你的工具的雏形
- 借助智能体为你的工具创建并运行全面的评测
- 与 Claude Code 这类智能体协作，自动提升你工具的性能

最后，我们总结在此过程中提炼出的、编写高质量工具的关键原则：
 - 选择合适的工具去实现（以及哪些不该实现）
- 用命名空间为工具划定清晰的功能边界
- 让工具向智能体返回有意义的上下文
- 针对令牌效率优化工具响应
- 用提示工程打磨工具的描述与规格

构建一套评测，能让你系统性地衡量工具的性能。你可以用 Claude Code 依据这套评测自动优化你的工具。
## 什么是工具？

在计算领域，确定性系统在给定相同输入时每次都会产生相同的输出；而非确定性系统——例如智能体——即便起始条件相同，也可能生成各不相同的响应。

传统上我们编写软件，是在确定性系统之间订立一份契约。例如 getWeather("NYC") 这样的函数调用，每次被调用时都会以完全相同的方式获取纽约市的天气。

工具是一类新型软件，它体现的是确定性系统与非确定性智能体之间的契约。当用户问"今天要不要带伞？"，智能体可能会调用天气工具、凭常识作答，甚至先追问一句你在哪里。有时，智能体还可能产生幻觉，甚至根本没能搞懂该怎么用一个工具。

这意味着，为智能体编写软件时，我们必须从根本上重新思考做法：不能再像给其他开发者或系统写函数和 API 那样去写工具、写 MCP 服务器，而要为智能体而设计它们。

我们的目标，是扩大智能体能够有效施展的"面积"——让它们借助工具、采取多种成功策略，去解决各种各样的任务。所幸根据我们的经验，那些对智能体最"顺手"的工具，最终对人来说也往往出奇地直观。

## 如何编写工具

本节介绍你可以如何与智能体协作，来编写并改进你交给它的工具。先快速搭起工具的雏形并在本地测试；接着运行一套全面的评测，用来衡量后续改动。与智能体并肩工作，你可以不断重复"评测—改进"的循环，直到智能体在真实任务上表现出色。

### 构建原型

如果不亲自动手，很难预判哪些工具智能体用起来顺手、哪些不顺手。先快速搭起工具的雏形。如果你用 Claude Code 来写工具（可能是一句话搞定），最好把工具所依赖的任何软件库、API 或 SDK（可能还包括 MCP SDK）的文档交给 Claude。对 LLM 友好的文档，通常能在官方文档站点上的扁平 llms.txt 文件里找到（这是我们的 API 对应的版本）。

把工具封装进本地 MCP 服务器或桌面扩展（Desktop extension，DXT），就能让你在 Claude Code 或 Claude Desktop 应用中连接并测试这些工具。

要把本地 MCP 服务器接入 Claude Code，运行 claude mcp add [args...]。

要把本地 MCP 服务器或 DXT 接入 Claude Desktop 应用，分别进入 Settings > Developer 或 Settings > Extensions。

工具也可以直接传入 Anthropic API 调用，用于程序化测试。

亲自试用这些工具，找出硌手的地方。收集用户的反馈，从而对工具要支撑的使用场景和提示词建立直觉。

### 运行评测

接下来，你需要通过运行评测来衡量 Claude 使用你工具的效果。先围绕真实世界的用法，生成大量评测任务。我们建议与某个智能体协作，帮你分析结果、找出改进工具的方法。完整的流程可参见我们的工具评测 cookbook。
（图：我们内部 Slack 工具的留出测试集表现）
生成评测任务

有了早期的雏形，Claude Code 就能快速探索你的工具，并造出几十组提示词与响应对。提示词应当源于真实世界的用法，并基于真实的数据源与服务（例如内部知识库和微服务）。我们建议你避开那些过于简单、流于表面的"沙箱"环境——它们无法用足够的复杂度去压测你的工具。好的评测任务可能需要多次工具调用——甚至几十次。

以下是一些好任务的例子：
 - 下周与 Jane 安排一场会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的记录，并预订一间会议室。
- 客户 ID 9182 反馈，他们单次购买尝试被扣了三次款。找出所有相关日志条目，并判断是否还有其他客户遭遇了同样的问题。
- 客户 Sarah Chen 刚刚提交了取消申请。准备一份挽留方案。请判断：(1) 他们为什么要离开，(2) 什么样的挽留方案最有吸引力，(3) 在提出方案前，有哪些风险因素需要我们留意。

以下则是一些较弱的任务：
 - 下周与 jane@acme.corp 安排一场会议。
- 在支付日志里搜索 purchase_complete 和 customer_id=9182。
- 找出客户 ID 45892 提交的取消申请。

每个评测提示词都应当配有一个可验证的响应或结果。你的验证器可以简单到对标准答案与采样响应做精确字符串比较，也可以高级到请 Claude 来评判响应。要避免验证器过于严苛——不要因为格式、标点或合理的替代表述这类无关差异，就否决正确的响应。

对每一组提示词—响应对，你还可以选择性地指定你期望智能体在解题时调用哪些工具，以便在评测中衡量智能体是否成功领会了每个工具的用途。不过，解题的正确路径可能不止一条，所以要尽量避免把策略规定得过细或过拟合。

运行评测

我们建议以程序化方式、通过直接调用 LLM API 来运行评测。使用简单的智能体循环（用 while 循环包裹交替进行的 LLM API 调用与工具调用）：每个评测任务一个循环。每个评测智能体应被赋予单个任务提示词和你的工具。

在评测智能体的系统提示词中，我们建议指示智能体不仅输出结构化的响应块（用于验证），还要输出推理块和反馈块。指示智能体在工具调用块和响应块之前输出这些内容，可能通过触发思维链（Chain-of-Thought，CoT）行为来提升 LLM 的有效智能水平。

如果你用 Claude 运行评测，可以打开 interleaved thinking 来获得类似的功能，可谓"开箱即用"。这有助于你探究智能体为什么调用或不调用某些工具，并突出工具描述与规格中需要改进的具体环节。

除了顶层准确率，我们还建议收集其他指标，例如单次工具调用与任务的运行时长、工具调用总次数、令牌总消耗量以及工具错误。跟踪工具调用有助于发现智能体常走的公共工作流，也为工具的合并整合提供一些机会。
（图：我们内部 Asana 工具的留出测试集表现）

分析结果智能体是你发现问题的好帮手，它能就各种问题给出反馈——从自相矛盾的工具描述，到低效的工具实现，再到令人困惑的工具 schema。不过要记住：智能体在反馈和响应中省略的内容，往往比它们写出来的更重要。LLM 并不总是把心里想的说出来。

观察智能体在哪里卡壳或困惑。通读评测智能体的推理与反馈（也就是 CoT），找出硌手之处。查阅原始记录（包括工具调用和工具响应），捕捉智能体 CoT 中未明确描述的任何行为。要读懂字里行间的意思；记住，你的评测智能体未必知道正确答案和策略。

分析你的工具调用指标。大量冗余的工具调用，可能说明分页或令牌上限参数需要调整到合适大小；大量因参数无效导致的工具错误，则可能说明工具需要更清晰的描述或更好的示例。我们在发布 Claude 的网页搜索工具时发现，Claude 会不必要地在工具的 query 参数后追加 2025，导致搜索结果产生偏差、性能下降（我们通过改进工具描述把 Claude 引回了正轨）。

### 与智能体协作

你甚至可以让智能体来分析你的结果并替你改进工具。只需把评测智能体的记录拼接起来，粘贴进 Claude Code。Claude 是分析记录、一次性重构大量工具的行家——例如，确保在有新改动时，工具的实现与描述仍然自洽。

事实上，本文的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评测搭建在内部工作区之上，复刻了内部工作流的复杂度，包含真实的项目、文档和消息。

我们依靠留出测试集来确保没有对"训练"用评测过拟合。这些测试集表明，我们还能挖出额外的性能提升——甚至超出"专家"工具实现所达到的水平，无论这些工具是研究人员手写的，还是 Claude 自己生成的。

下一节，我们将分享从这一过程中学到的一些心得。

## 编写高效工具的原则

本节把我们学到的东西提炼成若干指导原则，用于编写高效的工具。

### 为智能体选择合适的工具

工具更多，未必结果更好。我们观察到的一个常见错误，是工具只是把现有软件功能或 API 端点包了一层——而不论这些工具是否适合智能体。原因在于，智能体相较于传统软件有其独特的"可供性"（affordances）——也就是说，它们感知自己能用这些工具采取哪些潜在动作的方式是不同的

LLM 智能体的"上下文"是有限的（即它们一次能处理的信息量有上限），而计算机内存则廉价且充裕。想想在通讯录里查找某个联系人的任务。传统软件程序可以高效地存储并逐个处理联系人列表，检查完一个再看下一个。

然而，如果 LLM 智能体用的工具会返回全部联系人，然后它还得逐令牌地通读一遍，那它就是在把有限的上下文空间浪费在无关信息上（想象你从第一页到最后几页逐页翻阅通讯录去找一个联系人——也就是暴力搜索）。更好也更自然的做法（对智能体和人类都一样）是先跳到相关的那一页（也许按字母顺序找到它）。

我们建议围绕特定的高价值工作流，精心打造少量工具，让它们与你的评测任务相匹配，再由此逐步扩展。在通讯录这个例子里，你或许会选择实现 search_contacts 或 message_contact 工具，而不是 list_contacts 工具。

工具可以合并功能，在底层处理多个相互独立的操作（或 API 调用）。例如，工具可以用相关元数据充实工具响应，或在单次工具调用中处理那些经常被串起来的多步任务。

以下是一些例子：
 - 与其实现 list_users、list_events 和 create_event 工具，不如考虑实现一个 schedule_event 工具，由它查找空闲时段并安排事件。
- 与其实现 read_logs 工具，不如考虑实现一个 search_logs 工具，只返回相关的日志行及其周边上下文。
- 与其实现 get_customer_by_id、list_transactions 和 list_notes 工具，不如实现一个 get_customer_context 工具，一次性汇总某位客户所有近期且相关的信息。

确保你构建的每个工具都有清晰、独特的用途。工具应当让智能体能够像人在拥有同样底层资源时会做的那样，把任务细分并加以解决，同时减少本来会被中间产物消耗掉的上下文。

工具过多或功能重叠，也会分散智能体的注意力，使其偏离高效策略。审慎而有选择地规划你要构建（或不构建）哪些工具，真的会有回报。

### 为工具划分命名空间

你的 AI 智能体可能会接触到几十个 MCP 服务器和数百个各不相同的工具——其中还包括其他开发者提供的。当工具在功能上重叠或用途含糊时，智能体就会搞不清该用哪一个。

命名空间（把相关工具归组在共同前缀之下）有助于在大量工具之间划出边界；MCP 客户端有时会默认这么做。例如，按服务为工具划分命名空间（如 asana_search、jira_search）以及按资源划分（如 asana_projects_search、asana_users_search），有助于智能体在正确的时机选到正确的工具。

我们发现，在前缀式与后缀式命名空间之间做选择，会对我们的工具使用评测产生不小的影响。影响因 LLM 而异，我们鼓励你依据自己的评测来选择命名方案。

智能体可能会调错工具，或用错的参数调用对的工具，或调用得太少，或错误地处理工具响应。通过有选择地实现那些名字能反映任务自然划分的工具，你同时减少了加载进智能体上下文的工具数量与工具描述数量，并把智能体计算从智能体的上下文卸载回工具调用本身。这降低了智能体犯错的总体风险。

### 让工具返回有意义的上下文

同样的道理，工具实现应当注意只向智能体返回高信号的信息。它们应优先考虑上下文的"相关性"而非"灵活性"，并避开底层技术标识符（例如 uuid、256px_image_url、mime_type）。而像 name、image_url、file_type 这样的字段，则更有可能直接为智能体的下游动作和响应提供依据。

智能体在处理自然语言的名称、术语或标识符时，也往往比处理晦涩难懂的标识符要成功得多。我们发现，仅仅把任意的字母数字 UUID 换成语义上更有意义、更易解读的语言（甚至只是一个从 0 开始编号的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精确度。

在某些情况下，智能体可能需要同时使用自然语言和技术标识符输出的灵活性，哪怕只是为了触发下游工具调用（例如 search_user(name='jane') → send_message(id=12345)）。你可以在工具里暴露一个简单的 response_format 枚举参数，让智能体自行控制工具返回"简明"还是"详细"的响应（见下图），从而同时满足两者。

### 针对令牌效率优化工具响应

优化上下文的质量很重要，但优化工具响应返还给智能体的上下文数量同样重要。

对于任何可能耗用大量上下文的工具响应，我们建议对分页、范围选取、过滤和/或截断做某种组合，并配以合理的默认参数值。对 Claude Code，我们默认把工具响应限制在 25,000 个令牌以内。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求会一直存在。

如果你选择截断响应，务必用有用的指示来引导智能体。你可以直接鼓励智能体采取更节省令牌的策略，比如在知识检索任务中做许多次小而精准的搜索，而不是一次宽泛的搜索。同样，如果某次工具调用报错（例如输入验证期间），你可以对错误响应做提示工程，清晰地传达具体且可操作的改进建议，而不是给出晦涩的错误码或堆栈回溯。

### 用提示工程打磨工具描述

现在我们来到改进工具最有效的方法之一：对你的工具描述和规格做提示工程。因为它们会被加载进智能体的上下文，所以它们能够共同引导智能体形成有效的工具调用行为。

在编写工具描述和规格时，想一想你会如何向团队里新来的同事介绍你的工具。考虑你可能不自觉地带入的上下文——特殊的查询格式、冷门术语的定义、底层资源之间的关系——并把它们明确写出来。通过清晰地描述（并用严格的数据模型强制约束）预期的输入与输出，来避免歧义。尤其是，输入参数要命名得毫不含糊：与其用名叫 user 的参数，不如用名叫 user_id 的参数。

有了评测，你就能更有把握地衡量提示工程带来的影响。即便对工具描述做细微的润色，也可能带来显著的改进。在我们对工具描述做了精确的改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评测上取得了当时最佳的表现，错误率大幅下降，任务完成度也得到提升。

你可以在我们的开发者指南中找到关于工具定义的其他最佳实践。如果你是在为 Claude 构建工具，我们还建议读一读工具是如何被动态加载进 Claude 系统提示词的。最后，如果你是在为 MCP 服务器编写工具，工具注解有助于披露哪些工具需要开放世界访问权限、哪些会做出破坏性更改。

## 展望未来

要为智能体构建高效的工具，我们需要把软件开发实践从可预测的确定性模式，重新定位到非确定性模式。

通过本文所述这套迭代的、评测驱动的方法，我们已识别出让工具走向成功的一贯模式：高效的工具被有意地清晰定义、审慎地使用智能体上下文、能在多样化的工作中组合使用，并让智能体直观地解决真实世界任务。

未来，我们预计智能体与世界交互的具体机制还会不断演进——从 MCP 协议的更新，到底层 LLM 自身的升级。只要对"为智能体改进工具"采取系统化、评测驱动的方法，我们就能确保：随着智能体能力越来越强，它们所用的工具也会与之共同演进。
