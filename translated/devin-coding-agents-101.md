# 编码智能体 101：真正把事情做成的艺术

时间是 2025 年。编码智能体并非魔法，但它们已经是我们最接近魔法的东西。我们注意到，一些工程师——尤其是资深到高级职员（senior-to-staff）级别——比其他人的上手速度更快。这里，我们分享一些来自客户与我们自身经验的要点。

关于本指南：

## 与产品无关

我们讨论的技巧能帮助你用好任何一款编码智能体。

## 战术层面

我们给出最喜欢的一些可落地建议。

## 技术层面

虽然编码智能体对许多人都有价值，但本指南是面向工程师撰写的。

开发者工具一直在快速演进。十年前，是自动补全与智能提示（autocomplete 和 intellisense），能够推荐方法名并完成程序化的重构。四年前，是 copilot 与 Tab 补全，能替你写下接下来几行代码。两年前，是生成式聊天机器人，能辅助你开发并为你生成整个文件。而今天，是自主智能体，能够从最初的描述出发，几乎不需要人工干预就交付最终的拉取请求（PR）。过去两年，我们通过打造 Devin 一直致力于实现这一愿景。如今，人们对自主智能体的兴趣正达到新的高度，尤其是在近期发布的一批同类产品之后 [1]。除 Devin 之外，近期发布的产品还包括 OpenAI 的 Codex 和 Google 的 Jules。像 Cursor、Claude Code 这类本地智能体可以在并行的多个工作区中运行，从而复制出类似的效果。这些智能体的形态多种多样，包括网页应用、移动应用，以及集成进 Slack、GitHub、Linear、Jira 等流行工具中。

虽然人类与 AI 助手配合所能达成的成果超过任何单独的 AI，但自主智能体端到端处理任务的能力带来了全新层次的多任务并行，把每一位工程师都变成了工程经理。

适应与这些新的 AI 同事高效协作需要一些时间。有意思的是，我们观察到，资深到高级职员级别的工程师往往上手最快、最熟练。最终，这些工具将在各个层级的工程工作中普及。基于我们的经验与客户反馈，我们希望分享关键洞见与经验教训，帮助每个人成功地把这些工具融入自己的工作流。

## 提示词基础

这些基本准则将帮助你在 2025 年与编码智能体高效互动。如果别的什么都记不住，至少记住这些。

### 告诉它怎么做，而不只是做什么

把智能体想象成一位决策未必可靠的初级编程伙伴。简单任务可以直接描述，但对更复杂的任务，要一开始就清楚说明你偏好的做法。提前把整体架构与逻辑告诉智能体，不仅能提高它成功的概率，还能减少你审查代码的时间，因为你事先已经熟悉了预期的实现方式。

#### 示例：

与其说"加上单元测试"，不如明确要测试的功能、指出重要的边界情况，并说清哪些东西需要被 mock（模拟），如果有的话。

### 告诉智能体从哪里入手

想一想如果这个任务由你自己来做，你会从哪里开始。即便不知道具体的文件名或函数名，也可以提到相关的代码仓库、文档以及涉及的关键组件。清楚地指出这些要素，能最大限度减少白费功夫与困惑。

#### 示例：

"请为我们的代码加上对 Google 模型的支持。你可以查看最新文档 [here](link)，并在 model groups 目录下新建一个实现文件"

### 做防御式提示

想象你把这个提示词交给一位新来的实习生。哪里最可能出现困惑或错误？预判这些点，主动澄清你的指令以避免歧义。

#### 示例：

"请修复我们搜索模块的 C++ 绑定，让它通过新的单元测试。注意，每次改完代码后你可能需要重新编译绑定，然后再测试。"

### 让智能体用上 CI、测试、类型检查和 linter

智能体的许多"魔力"来自它能修正自己的错误并针对错误信息反复迭代。通过类型检查器、linter、单元测试等工具提供强有力的反馈回路，能大幅提升它的表现。考虑用带类型的 Python 而不是普通 Python，或用 TypeScript 而不是 JavaScript。教会你的智能体如何运行常见的检查与测试，确保它拥有所有必要的依赖包与访问权限。如果智能体能操作浏览器，请给出运行你前端开发环境的清晰指令。

#### 示例：

我们团队从大部分是无类型的 Python SDK 全面转向了带类型的 SDK（这本身也是适合交给编码智能体的好任务）。

### 发挥你的专业能力

当你熟悉自己的代码库时，上面的一切都会变得更容易。即便是简单的任务，你对逻辑和结果的核验能力也大有帮助。人的监督依然不可或缺——最终，代码正确与否的责任由你承担。随着这些工具日益强大，拥有权和核验仍将是人类工程师的关键职责。

## 在工作流中使用智能体

## 委派更大的工单

-->

随着你的拉取请求（PR）规模与复杂度增长到不止几个文件，一次性处理它们就变得有挑战了。然而，真正掌握如何委派中大型任务（通常 1-6 小时的工作量）正是自主智能体带来最高投资回报（ROI）的地方。你省下的不是几分钟，而是数小时的生产力。较小的任务也许能轻松搞定，但把智能体的能力拉伸到处理更大的任务，才能带来最大的回报。

### 自动化你的初稿

对于体量可观的任务，让自主智能体为你的 PR 生成初稿，可以推动进展并大幅减轻你的工作量。这里能否成功，取决于你是否在一开始就清楚传达你期望的做法。把自己当成指导初级开发者的架构师。清晰、详细的指令有助于避免把时间浪费在纠正智能体代码中的根本性误解上。

| 领域 | 起草 | 精修 |
|---|---|---|
| 新闻业 | 记者收集初步信息，撰写文章初稿 | 编辑审阅草稿、核对事实、打磨润色，最终定稿发表 |
| 餐饮 | 流水线厨师准备食材并做出初步菜品 | 副主厨添加调味、调整菜品口味，然后在送给食客前把关 |
| 编程 | 自主智能体根据初步计划着手任务，产出初版解决方案 | 人类开发者审阅草稿 PR、给出反馈，在合并前手动细化和完善 |

🛑 记住，大型任务还不能完全无人值守（暂时）。对更有挑战性的任务，要预期多轮反馈；对最终的打磨，也要预期一些人工细化。现实的目标是大约节省 80% 的时间，而非完全自动化，你的专业能力对核验和最终质量保证依然至关重要。

### 共同制定 PRD

对于复杂或定义模糊的任务，与你的自主智能体协作制定一份详细计划可能非常有效。一开始并不清楚每个细节或需求，这完全没关系。可以先提示智能体去探索发现类问题，比如"我们的认证系统是如何运作的？"或"哪些服务可能会受影响？"你还可以让智能体找出具体的相关代码目标，供你尽早确认。

某些智能体，比如 Devin 和 Claude Code，提供了专门的规划模式，专注于阅读和探索现有代码，而不是立即修改它。如果你希望在委派任务前做更充分的准备，像 deepwiki.com 和 Devin Search 这样专门的代码库搜索工具，可以快速给出关于你代码库的洞见，帮助简化流程。

### 设置检查点

对于分多个部分的任务，尤其是涉及多个代码库的任务，要在过程中设立清晰的检查点：

Plan → Implement chunk → Test → Fix → Checkpoint review → Next chunk

在每一个重要阶段之后明确要求暂停，尤其是跨多个层次（例如数据库、后端、前端）构建的复杂功能。利用这些检查点来确认实现符合你的预期、澄清疑问（例如"解释一下认证流程并确认它的安全性"），并尽早纠正方向以避免问题层层累积。

#### 示例：

"我希望你实现这个跨越我们数据库、后端和多个前端界面的功能。请先规划所需的数据库 schema 改动，完成后告诉我，我好执行迁移。" -> "现在请实现后端改动并添加测试，确保 XYZ 能正常工作。完成后告诉我" -> "现在在我们的网页和移动端界面里实现调用新后端端点的改动"

### 教会它自我验证

在给反馈时，不要只是指出问题（"这个函数不工作"）。清楚说明你的测试流程，让智能体能够独立验证未来的任务。对于你会反复用到的测试模式，把这些整合进智能体的长期知识库（参见"添加到智能体的知识库"）。

#### 示例：

在 Devin 中，我们会主动提示用户把关键的测试流程保存到智能体的持续记忆中，从而简化未来的交互。

### 提高 AI 高频改动区域的测试覆盖率

目前，智能体还无法完全交互式地彻底测试所有场景。在 AI 大量修改的区域增强测试覆盖，能让你对智能体的产出更有信心。扎实的测试意味着看似正确的代码可以被放心合并，无需担忧。

#### 示例：

## 自动化工作流

智能体响应传入事件的速度远超人类，而且它们比人类同事更愿意做枯燥、重复的工作。

### 为最高频的重复工作创建快捷方式

工程团队经常遇到重复性的例行任务。这些正是交给智能体自动化的完美候选。常见的例子包括：

 - feature flag removal（功能开关移除）

 - dependency upgrades（依赖升级）

 - fixing and adding tests on new feature PRs（在新功能 PR 上修复并添加测试）

要高效地做这件事，通常由一位有经验的工程师为这些场景创建一套健壮、可复用的提示词模板 [2]。在 Devin 中，这类模板被称为 playbook（行动手册），可以重复运行。

虽然存在专门用于快速代码评审的工具 [3]，比如 Greptile 和 CodeRabbit，但自主智能体也可以是提供更准确洞见的有趣选择，尤其是当它们已经为你的代码库功能建立索引时。

#### 示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把它提交到代码库中。然后，我们不写传统的 lint 规则来捕捉这些错误（这往往做不到），而是让智能体在每一个新 PR 上运行，检查这些错误。

### 接入事故与告警

你还可以设置自主智能体，让它们针对特定事件自动触发。例如，Devin 提供了易用的 API，而其他智能体可以通过 CLI 命令集成进自定义工作流。这些设置与 MCP（模型上下文协议）搭配使用时效果尤佳，可用于摄取第三方的错误日志。

⚠️ 在给生产服务中的问题做初步分诊（triage）时，AI 的调试能力并不算好。与其让 AI 在 bug 一出现就端到端地修复它们，通常更实际的做法是让 AI 只标记出最可疑的错误、改动等。

## 定制化与性能提升

### 环境搭建

没有什么比一个不完整或不匹配的环境更能拖慢智能体。为保持一切顺畅运行，让你的智能体环境与团队环境严格对齐。这包括语言版本、依赖包和自动化检查。例如，智能体环境中应安装 pre-commit，环境配置（密钥、语言版本、虚拟环境、浏览器登录态）应通过 .envrc 或 .bashrc 的自定义配置等工具自动加载。

### 添加到智能体的知识库

如果你的智能体犯了一些常见错误，那正是把你的反馈固化成智能体知识库内容的好时机。在 Devin 中，有一套专门的知识管理系统。许多产品提供 .rules 文件、.md 文件供智能体永久摄取。不要只给它关于你所用框架的准则，还要告诉它你项目的整体架构。告诉它不同类型的任务通常要做哪种测试，如何运行重要命令，以及你推荐使用哪些工具。

## 自主智能体的局限

### 调试能力有限

缺陷报告可能看似简单。但许多缺陷往往不仅需要访问数据库和日志，还需要超出当今大多数 AI 智能体的调试能力。如果用 AI 辅助调试，我们建议让它给出可能根因的清单，而不是尝试自己调试并修复一切。然后，人可以依据自身经验判断哪一个才是真正的根因。但一旦原因明确，智能体在实现修复上仍然可以相当有帮助。

### 细粒度视觉推理能力差

总体而言，当今的模型还不具备在匹配设计截图或 Figma 原型稿所需细节层面上的出色视觉推理能力。它们在最能用代码描述的视觉内容上最为可靠（例如，把 Figma 的代码给它）。如果你希望它匹配你的视觉风格，就应该使用带有可复用组件的优秀设计系统。

### 知识截止

每当你想要使用一个新库时，都应该明确地把它指向最新的文档。否则，大多数智能体会因为预训练基础模型的知识截止而套用这些库的旧模式。如果你把它指向文档，一个好的智能体可以克服这一点，但你必须留意这件事（记住，智能体甚至不知道这些库已经有了新版本）。

实践考量

## 管理时间与减少损失

并非每次使用智能体都会成功。2025 年，这些智能体的产出结果存在真实的波动。工作的一部分就在于学会如何使用智能体，以最大化遇到成功结果的概率，同时把浪费的时间和令牌降到最低。

### 愿意更早止损

刚开始用智能体的人常犯的一个错误是，即便智能体的工作正在跑偏，也非要让这次交互成功。如果你发现自己心里想"它在无视我的指令"或"这东西在原地打转"，那就应该果断结束这次对话或手动接管。继续发更多消息，更可能说明你的任务本身的复杂度超出了智能体的能力，而不是某个可以纠正的简单错误。

### 让你的试验多样化

如果你刚开始接触智能体，我们建议一开始就分散下注。尝试各种各样的提示词和想法。对智能体天生表现良好的任务类型加倍投入——对它们做不好的则果断止损。不必强求你的智能体每次都必须成功。

### 没有进展时就重新开始

对于智能体，重来一遍是正确答案的几率要比对人高得多。如果你给了智能体一个任务，而它在处理反馈或纠正方向上挣扎，那么换一个新智能体、把所有指令一开始就给全，往往能更快成功。智能体纠正一个搞乱的环境的能力，远比它从零写出新代码的能力要差。

实践考量

## 安全与权限

### 为你的智能体创建账号

一次性邮箱有助于安全地测试各种站点。如果你的智能体需要访问云资源，请为它创建自定义的 IAM 角色。

### 给它一个开发/预发环境

理想情况下，智能体使用与你团队工程师相同的测试环境。我们建议完全避免给它访问生产服务的权限。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

尽可能给它只读访问权限。我们发现，凡是对接外部服务的脚本，仍由人工手动运行会更有帮助。

## 巨变在前

我们坚信软件工程师不会消失。即便编码智能体变得更聪明、更有能力，深厚的技术专长和对代码库的深入了解依然无比宝贵。对你的项目、你的系统和你的代码的真正拥有权，如今比以往任何时候都更关键。在我们团队，工程师被期望在监督多个系统的同时，仍保持深入的理解和审慎的判断。当自动化放大你的影响力时，并行处理多项任务的能力将不仅成为可能，更会成为必需。我们很高兴分享我们在为自身组织准备这场转变过程中所积累的洞见，让你和你的团队也能在日新月异的软件开发世界中蓬勃发展。
