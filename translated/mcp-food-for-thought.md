# 关于 MCP 的一些思考

模型上下文协议（Model Context Protocol，MCP）如今是一件举足轻重的大事。它已经成为让 LLM 访问他人所写工具的事实标准——这当然也把它们变成了智能体。但是，为一个新的 MCP 服务器编写工具很难，因此人们常常提议把现有 API 自动转换为 MCP 工具，通常借助 OpenAPI 元数据来完成（参考文献 1、2）。

以我的经验，这行得通，但效果并不好。原因如下：

## 智能体不擅长处理大量工具

众所周知，VS Code 对工具有 128 个的硬性上限——但许多模型远在这个数字之前就会在准确调用工具上力不从心。此外，每个工具及其描述都会占用宝贵的上下文窗口空间。

大多数 Web API 在设计时并没有考虑这些约束！当 API 从代码中调用时，一个产品领域有几十个 API 完全没问题，但如果把这些 API 逐个映射成 MCP 工具，结果可能并不理想。

从零开始设计的 MCP 工具通常比单个 Web API 灵活得多，每个工具能够承担多个单独 API 的工作。

## API 会迅速撑爆上下文窗口

设想一个 API 每次返回 100 条记录，而每条记录都非常宽（比如 50 个字段）。把这些结果原样发给智能体会消耗大量 token；即便一个查询只需要少数几个字段就能满足，但每个字段最终都会被塞进上下文窗口。

API 通常按记录数分页，但记录大小可能千差万别。一条记录可能包含一个占用 10 万 token 的大文本字段，而另一条可能只有 10 个。把 API 结果直接塞进智能体的上下文窗口是一场赌博：有时能行，有时会爆掉。

数据格式也可能是个问题。如今大多数 Web API 返回 JSON，但 JSON 是一种非常低效的 token 格式。以下面这段为例：

```json
[
  {
    "firstName": "Alice",
    "lastName": "Johnson",
    "age": 28
  },
  {
    "firstName": "Bob",
    "lastName": "Smith",
    "age": 35
  }
]
```

对比 CSV 格式的同一份数据：

```csv
firstName,lastName,age
Alice,Johnson,28
Bob,Smith,35
```

CSV 数据要简洁得多——每条记录消耗的 token 只有一半。通常，CSV、TSV 或 YAML（用于嵌套数据）是比 JSON 更好的选择。

这些问题并非不可逾越。你可以设想自动添加让智能体投影字段的工具参数、自动截断或概括大结果、自动把 JSON 结果转换为 CSV（或用于嵌套数据的 YAML）。但我见过的大多数服务器，这些事一件都没做。

## API 没有充分利用智能体的独特能力

API 返回结构化数据，供程序化消费。这往往是智能体对工具调用的期望……但智能体还能处理其他更自由形式的指令。

例如，一个 ask_question 工具可以对某些文档执行 RAG（检索增强生成）查询，然后以纯文本返回信息，用来指导下一次工具调用——完全跳过结构化数据。

或者，调用 search_cities 工具可以返回结构化的城市列表，以及下一步该调用什么的建议：

```csv
city_name,population,country,region
Tokyo,37194000,Japan,Asia
Delhi,32941000,India,Asia
Shanghai,28517000,China,Asia
```

> 建议：如需更具体的信息（天气、景点、人口统计），可尝试调用 get_city_details 并传入 city_name 参数。

这种分层与工具链式调用在 MCP 服务器中非常有效，而如果你把 API 自动转换成工具，就会完全错过它。

## 如果智能体需要调用 API，它本可以直接调用

像 Claude Code 这样的智能体如今在编写并执行代码（包括调用 Web API 的脚本）方面能力相当强。有些人甚至据此主张：MCP 根本不需要了！

我不同意这个结论，但我确实认为我们应该「把功夫下在趋势所在之处」。智能体的沙箱化正在快速改善，如果智能体直接调用 API 变得既简单又安全，那我们倒不如就这样做，省去中间环节。

## 结论

智能体与 API 的典型消费者有着本质区别。从现有 API 自动创建 MCP 工具是可能的，但这样做效果大概率不好。当拿到的是「为智能体独特能力与局限而设计」的工具时，智能体的表现才是最好的。
