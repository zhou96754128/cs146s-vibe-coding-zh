# 拿来说明 01 · 把"术语表"从泛泛词表做成可校验锚点表

> 对应要求：术语表 ≥50 条且全文一致（Vibe Coding / Scaffolding / Context Engineering 译法统一）。

## 原文（任务要求）

> 术语表 ≥ 50 条且全文一致（如 Vibe Coding / Scaffolding / Context Engineering 的译法统一）。

## Prompt（三次迭代的真实过程）

**第 1 版（失败）**
> 帮我列一份这门课的术语表。

结果：产出泛泛，全是 "AI / 模型 / 代码" 这类通用词，对翻译一致性没有任何约束力。

**第 2 版（可用）**
> 只列这门课**特有、且容易被译歪**的概念，并给出每个词的**统一译名**，注明哪些必须保留英文。

结果：可用，但仍是一张平铺清单，不便按场景校验。

**第 3 版（最终采用）**
> 按类目分组（核心范式 / 安全 / 工程实践），每行给：英文、标准译名、备注；**产品名保留英文**，**缩写保留英文并在首次出现时给出中文全称**。

## 产出（仓库内可核对）

`glossary/术语表.md` —— **94 条**（要求 ≥50），按类目分组的表格，可直接被翻译流程引用、被质检脚本校验。

摘录（形态示意）：

| 英文 | 标准译名 | 备注 |
|---|---|---|
| Vibe Coding | Vibe Coding | 保留英文（专有范式） |
| Scaffolding | 脚手架 | 统一译"脚手架"，不译"支架" |
| Context Engineering | 上下文工程 | 统一 |
| Prompt Injection | 提示注入 | 统一 |
| SAST / DAST | SAST / DAST | 缩写保留英文，首次给中文全称 |

## 对比（改动前后）

| | 第 1 版 | 第 3 版（采用） |
|---|---|---|
| 产物形态 | 平铺词表 | 按类目分组、可机器校验的表格 |
| 对翻译的约束力 | 无（通用词） | 强（逐词给统一译名 + 保留英文规则） |
| 可校验性 | 不可校验 | 质检脚本按表逐条比对，未命中即报错 |
| 条数 | 少量通用词 | 94 条锚点 |

## 这条说明了什么

**关键决策：术语表必须是独立产物，先冻结、再翻译。**

理由：让 AI"边翻边保持术语一致"，在长文上必然漂移——同一页内都会前后不一。把术语抽出来冻结成一张**可机器校验**的锚点表，是保证 31 个页面译名统一的唯一可行做法。这也是本项目最重要的一条经验：**先定标准，再干活。**
