# 拿来说明 03 · 把"感觉还行"变成"有据可查"：质检脚本与误报治理

> 对应要求：AI 使用质量（质量抽检有据）；无大段漏译/机器感硬伤。

## 原文（任务要求）

> aiUsage AI 使用质量（20 分）：多轮迭代、prompt 优化、**质量抽检有据**（AI 日志佐证）。

## 关键判断

"我觉得翻得挺好"不是证据，**脚本输出的报告才是**。因此写了 `pipeline/qc.py`，对 32 个译文文件做四类自动检查：

- **A 结构对等**：源/译文的标题数、表格数、代码块数、链接数是否一致；
- **B 残留英文**：正文里是否还有整句英文未译（排除代码块、行内代码、URL、表格载荷）；
- **C 术语落地**：术语表条目在译文中是否真的用了标准译名；
- **D 空壳页**：源文件本身无正文的页面，译文是否有「无正文」说明。

## 过程：误报治理（比写脚本更花时间）

**首版结果**：13 项结构差异 + 一批"残留英文"，看着像灾难。

**逐条对账**（产出 `out/qc-struct-audit.md`，8,242 字节）后发现差异分两类，**都不是漏译**：

1. 源站抓取时混入的**框架块**（侧栏导航、页脚推广位、"about the author"），译文按资料包用途剔除；
2. 源页用**重复 H4** 承载 10 个攻击场景（H4 33→23），译文改为场景级标题并**保留全部表格**。

**三处典型误报与修法**：

| 误报 | 真相 | 修法 |
|---|---|---|
| 代码块里的英文被报"未译" | 带缩进的代码围栏被当成正文 | 先标记围栏行号并跳过 |
| `context-rot` 页 13 处英文 | 是**原文逐字引用的模型退化输出**（证据） | 加 `KEEP_EN_QUOTES` 白名单 |
| `mcp-introduction` 的 `prompt:`/`tools:` | 是 JS 请求载荷与产品名对比导航 | 新增两条正则规则识别 |

## 硬伤修复（真问题）

`pipeline/qc.py` 之外，另写扫描脚本全量查 32 个译文（185,301 字符），查出 **7 项真硬伤**并批量修复：

- **30 处被转义的 HTML 实体**（`&gt;`/`&lt;`/`&amp;`）：判据是**源侧同类实体计数为 0**，证明这些全是翻译过程产生的伪影，可安全还原；
- **2 处泄漏的内部标记**（AI 生成内容时把内部状态标记写进了正文）：删除；
- **1 处真错字**（"的的"）。

**修复前后**：硬伤 7 项 → **0 项**；最终质检：**结构 0 ｜ 残留英文 0 ｜ 术语 0 ｜ 缺译文 0**。

**还有一次"判据说谎"**：修复后复检又报 2 项——`devin` 的"叠字"其实是合法语法（"现在在"），`mcp-server-authentication` 的"码内中文"其实是代码里的中文注释。问题在判据太粗，不在译文。于是收紧检查规则，复检归零。

## 对比（改动前后）

| | 修复前 | 修复后 |
|---|---|---|
| 硬伤 | 7 项 | 0 项 |
| 结构差异 | 13 项（含误报） | 0 项（差异已逐条定性并解释） |
| 残留英文 | 一批（含 3 类误报） | 0 项 |
| 依据 | 主观感觉 | `out/qc-report.md` + `out/qc-struct-audit.md` |

## 这条说明了什么

**抽检脚本的误报和译文的错误一样要治理。** 误报不处理，报告就没人信；而**"改译文去迎合错误判据"是最坏的做法**——当判据与事实冲突时，要改的是判据，不是事实。
